## Top-3 (for spec-writer)

### 1. techdocs-mkdocs-code-exec-v2: TechDocs RCE via mkdocs.yml (CVE-2026-88064, CVSS 8.8)
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** `plugin-techdocs-node` is a plugin we actively run, and this is an authenticated-user-to-RCE path on the Backstage backend process, which shares the backend's Kubernetes service account and Vault token — critical blast radius for tenant `admins`. This is a genuinely new, higher-severity CVE (CVSS 8.8 vs. 7.7), not a rehash: the existing `proposals/techdocs-mkdocs-code-exec/` proposal addresses a different CVE (CVE-2026-29186, fixed at 1.14.3) via a different vector (disallowed plugin/hook directives). CVE-2026-88064 is exploitable through unsafe YAML tags, `markdown_extensions` config, theme options and `extra_templates` — a broader attack surface — and is only fixed at 1.14.6/1.15.4, i.e. versions above the prior proposal's target fix. The prior proposal's fix is necessary but not sufficient; this proposal should be scoped as a follow-on/superseding hardening pass (bump to >=1.14.6/1.15.4 and extend the input-validation coverage), explicitly cross-referenced to the existing proposal rather than duplicating it. No impact on tenant `labs` (mctl-portal runs only in `admins`).
**Source:** CVE-2026-88064, inbox "Source: cve" section; cross-check against `proposals/techdocs-mkdocs-code-exec/requirements.md` (CVE-2026-29186, fixed 1.14.3).

### 2. backstage-1-55-0-scaffolder-recovery-eval: Evaluate Backstage v1.55.0 (scaffolder task recovery + perf, gated on compat)
**Category:** performance
**Impact:** 3
**Effort:** 4
**Rationale:** v1.55.0 adds scaffolder task recovery and backend performance improvements — directly relevant since scaffolder is our tenant-onboarding path into mctl-gitops/Argo Workflows and a stuck/failed task today has no documented recovery story. This is a distinct release from the already-proposed `backstage-1-54-7-oauth-normalization` (which targeted a different, auth-specific patch) so it is not a rehash. However it ships breaking changes to deprecated catalog APIs and an Elasticsearch 8 requirement; our architecture does not list Elasticsearch as our search backend, so that requirement needs an explicit compatibility check before adoption, and ADR 0001 plus `architecture.md` both caution against adopting a fresh Backstage release before community-plugins compatibility is confirmed (~1-2 weeks). The spec should therefore frame this as a staged evaluation (validate custom plugins — kubernetes, observability, scaffolder, techdocs — in a lower environment first, confirm no forced ES8 dependency applies to us) rather than an immediate production bump. No `labs`-tenant impact (admins-only service).
**Source:** "Backstage v1.55.0" entry, inbox "Source: github releases" section.

### 3. mctl-service-config-lookup-gap: mctl_get_service_config fails to resolve admins/mctl-portal
**Category:** refactor
**Impact:** 2
**Effort:** 2
**Rationale:** This cycle is the first time `mctl_get_service_config` was called for admins/mctl-portal, and it returned "service not found" — a harder failure than the previously-known null `service` field on the ArgoCD status call (tracked in `proposals/argocd-service-field-gap/`). It may share the same underlying service-registration gap, or it may indicate a separate config-registry issue distinct from the ArgoCD Application labels; either way it is new evidence that platform tooling cannot fully introspect this service, which risks silently breaking future automation (this very agent pipeline included) that depends on `mctl_get_service_config`. Recommend the spec-writer first determine whether this is the same root cause as `argocd-service-field-gap` (in which case fold it in as an expanded acceptance criterion there) or a distinct registry gap (in which case scope a small, separate fix) — do not implement it twice. No `labs`-tenant interaction.
**Source:** "mctl_get_service_config for admins/mctl-portal returned an error" entry, inbox "Source: mctl metrics" section.

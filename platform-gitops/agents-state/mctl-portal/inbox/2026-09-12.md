## Top-3 (for spec-writer)

### 1. backstage-1-54-7-oauth-normalization: Adopt Backstage v1.54.7 patch (OAuth profile normalization fix)
**Category:** security
**Impact:** 3
**Effort:** 2
**Rationale:** mctl-portal's whole SSO flow depends on Dex JWT/OAuth, and this upstream patch fixes profile normalization when processing email-verification information in that exact code path — a correctness/identity issue directly on our auth surface. It is a patch-level release within the 1.x line (not a major bump), so it does not conflict with ADR 0001's "no major on release day" guardrail, and no existing proposal (`backstage-1-50-4-patch`, `backstage-v1-50-4-security-patch`, `backstage-v1504-security-upgrade`, `backstage-catalog-security-patch`) targets 1.54.x — this is a genuinely newer version, not a rehash.
**Source:** Backstage v1.54.7 release notes (11 Sep 2026), https://github.com/backstage/backstage/releases/latest

### 2. portal-log-pipeline-gap: Investigate zero-log-line gap in mctl-portal observability pipeline
**Category:** refactor
**Impact:** 3
**Effort:** 3
**Rationale:** `mctl_get_service_logs` has returned 0 lines for mctl-portal for at least two consecutive daily cycles (2026-09-05 and 2026-09-12) even though the app is Healthy/Synced and presumably serving traffic — this is a pattern, not a one-off blip. If the log-shipping path (Loki/Backstage backend logging) is actually broken, on-call has no log visibility during an incident, which undercuts the observability plugin/Prometheus-Loki-Grafana investment described in the architecture. No existing proposal covers this; effort is mostly investigation (log level, shipper config, query scope) before any fix.
**Source:** "Service logs (mctl-portal, admins, last 24h)" — mctl metrics section, 2026-09-12 inbox.

# Design: issue-45-docs-the-landing-page-instructs-a-bearer

## Current state

### The page is one document written for two readers

`public/index.html` is a 319-line static file served by three explicit routes in
`src/api/server.ts:188-206`; there is no catch-all, and the comment at
`src/api/server.ts:165-172` is explicit that an undeclared path meets the auth
gate instead. The file is plain HTML with one inline script
(`public/index.html:271-315`) that does three things: applies the stored theme,
sets `#mcp-url` and every `.mcp-url-slot` from `window.location.origin + "/mcp"`,
and wires `#copy-url`. Styling comes from two vendored sheets,
`public/assets/tokens.css` and `public/assets/components.css`; the tokens file is
generated by `scripts/sync-tokens.mjs` from a pinned `https://ui.mctl.ai/0.5.0/mctl.css`
and verified in CI by `npm run check:tokens` (`.github/workflows/ci.yml`).

Section by section, the page today is:

| Lines | Section | Reader |
|---|---|---|
| 59-77 | Hero, endpoint, `Copy MCP URL` | user |
| 79-106 | "What it adds to the Seerr stack" | user |
| 108-137 | "How a request travels" | user |
| 139-174 | "MCP tools" (`id="tools"`) | user |
| 176-198 | "Connecting to Seerr" | mixed |
| 200-223 | "Set it up" (`id="setup"`) | mixed, and wrong |
| 225-260 | "Questions" | mixed |

### The instruction that cannot be followed

`public/index.html:206-213` is step 1 of "Set it up":

```
<li><strong>Add the MCP server.</strong> Point your client at the endpoint above and give it the
  bearer token you were issued.
  <pre><code>{
  "seerrsense": {
    "serverUrl": "<span class="mcp-url-slot">https://seerrsense.mctl.ai/mcp</span>",
    "headers": { "Authorization": "Bearer &lt;your token&gt;" }
  }
}</code></pre>
```

Two independent reasons this fails on the hosted server. First, the shared token
is disabled: `loadAuthSettings` computes
`legacyEnabled = parsed.SEERRSENSE_LEGACY_TOKEN_ENABLED !== "false"` and passes
`undefined` as `legacyToken` when it is off (`src/auth/config.ts:66-68`), so no
value the operator could "issue" is accepted. Second, an OAuth client does not
send a hand-set header at all: it discovers the authorization server from the
`WWW-Authenticate` challenge and the RFC 9728 document served at
`src/auth/routes.ts:264-271`, then runs the code flow in
`src/auth/routes.ts:273-506`. The snippet is not merely stale advice; it is a
step with no correct value to fill in.

Note that this `<pre>` is also the page's only `.mcp-url-slot`
(`public/index.html:210`). The script's
`document.querySelectorAll(".mcp-url-slot")` loop (`public/index.html:300-302`)
tolerates zero matches, so deleting the snippet is safe, but the endpoint then
appears only in the hero's `#mcp-url`.

### Operator material addressed to a user

"Connecting to Seerr" (`public/index.html:176-198`) is three cards. The first is
correct and user-facing: attach your own instance at `/account`. The second and
third are not:

- `CF_ACCESS_CLIENT_ID` / `CF_ACCESS_CLIENT_SECRET` (`public/index.html:189`) are
  operator process env, parsed at `src/core/config.ts:20-21` and applied to the
  *household* client. A hosted user supplies the same two values as form fields
  on `/account` (`public/account.html:70-79`), which `src/api/account.ts:84-118`
  seals per user with `seal(...)` and `TenantResolver` later unseals per request
  (`src/providers/seerr/tenants.ts:65-70`). Telling a user to "set" them is
  telling them to do something they cannot do.
- `NEBIUS_API_KEY` (`public/index.html:194`) is purely a self-hosting switch
  (`src/core/config.ts:18-19`).

The "Questions" section repeats it: "How is access controlled?"
(`public/index.html:241-247`) describes both the bearer token and "an explicit
list of addresses" — the `SEERRSENSE_ALLOWED_EMAILS` set built at
`src/auth/config.ts:88-94` — which is exactly what #44 replaces. "Can I
self-host it?" (`public/index.html:254-258`) closes with "See the repository for
the full list", which is a pointer to a README whose relevant sections are empty.

### The README has the holes this material fits

`grep -n "TBD" README.md` returns lines 87, 122, 186, 189, 234, 237, 240 —
`## Quick Start`, `## MCP`, `## REST API`, `## Architecture`, `## Development`,
`## Deployment`, `## Roadmap`. The prose that does exist is good: the
Configuration table (`README.md:89-119`) already documents `CF_ACCESS_CLIENT_ID`,
`CF_ACCESS_CLIENT_SECRET`, `NEBIUS_API_KEY` and every OAuth variable;
`## Whose Seerr` (`README.md:124-153`) explains tenant resolution; `## Web`
(`README.md:155-183`) explains the vendored tokens; `## Security Model`
(`README.md:191-231`) explains scopes, CIMD, PKCE and refresh rotation. The
missing sections are exactly the ones a self-hoster reaches for first.

The facts needed to write them are all in the clone: `Dockerfile` (node:22-slim,
`EXPOSE 8787`, healthcheck on `/healthz`), `.github/workflows/release-binaries.yml:26-32`
(four bun-compiled targets), `src/index.ts:9-19` (`stdio` / `--stdio`),
`src/core/config.ts:35-40` (`assertHttpConfig`), `src/api/server.ts:285-360`
(four REST endpoints), `src/api/account.ts:49,64,127` (three account endpoints),
`src/auth/routes.ts:255-271` (four discovery documents), `src/auth/config.ts:15-18`
(three scopes), and `package.json` scripts.

### What the tests already lock down

`tests/landing.test.ts` (204 lines) builds the real server with `buildServer()`
and a stubbed household Seerr client, then asserts on `app.inject` payloads. It
already guards: `<title>SeerrSense` and the literal `seerr:request`
(`:31-32`), OpenGraph tags (`:35-47`), asset content types (`:49-60`), the
no-JS render and `id="theme-toggle"` (`:62-78`), the absence of `ui.mctl.ai`
and the tokens-before-components link order (`:80-90`), the generated-tokens
banner (`:92-111`), `window.location.origin + "/mcp"` (`:113-116`), the absence
of a catch-all (`:118-133`), `class="flow-scroll"` and `class="table-scroll"`
(`:159-170`), and the privacy/terms links (`:193-197`). There is no assertion
about setup copy, so the current page's broken step passes CI today.

## Proposed solution

Split by reader. Four files change; nothing under `src/` does.

### 1. `public/index.html` — the person who signs in

**Delete** the "Connecting to Seerr" section (`:176-198`) and the "Set it up"
section (`:200-223`) and **replace both with one section** carrying
`id="setup"`, so the top-bar link at `public/index.html:46` and any external
`#setup` deep link keep resolving. The section reuses the existing `.steps`
list style (`public/assets/components.css:364-374`) — no CSS change, so
`npm run check:tokens` is untouched and the page keeps its zero-third-party-sheet
property.

Three `<li>` steps, in the order that produces the fewest surprises:

1. **Add the connector.** Both vendor paths spelled out.
   - claude.ai: *Customize → Connectors → "+" → Add custom connector*, paste the
     MCP URL, *Add*. Free allows one custom connector; Pro and Max are
     unrestricted; on Team and Enterprise an owner adds it under *Organization
     settings → Connectors* and members press *Connect*.
   - ChatGPT: *Settings → Security and login → Developer mode*, then
     *Plugins → "+"*, create an app with the MCP URL. Web only, on Plus, Pro,
     Business, Enterprise and Education.
   The MCP URL is rendered in a `<code class="mcp-url-slot">` so the existing
   script (`public/index.html:300-302`) keeps filling it from the origin — the
   slot survives the deletion of the JSON snippet rather than disappearing with
   it.
2. **Sign in with Google.** Happens on the first *Connect*; one consent screen
   names the client and what is granted (the flow at `src/auth/routes.ts:412-446`).
   No token to copy anywhere — stated positively, without the words "bearer
   token", so the page never reintroduces the string the test forbids.
3. **Attach your Seerr** at `/account`: address, API key (*Overseerr → Settings
   → General → API Key*), and — only if that Seerr sits behind Cloudflare Access
   — the two service-token fields, described as *fields on the page*, never as
   variables. Say the page tests the credentials against the instance before
   saving (`src/api/account.ts:93-102`), and that skipping this step is
   recoverable: the tools reply with the "No Seerr is connected" message from
   `src/providers/seerr/tenants.ts:106-109` and point at `/account`.

**Keep** the hero (`:59-77`), "How a request travels" (`:108-137`, whose
`.flow-scroll` is asserted at `tests/landing.test.ts:159-169`) and "MCP tools"
(`:139-174`, whose `.table-scroll` and `seerr:request` chip are asserted at
`tests/landing.test.ts:32` and `:159-170`).

**Tighten** "What it adds to the Seerr stack" (`:79-106`) from three cards to
two: keep "Resolution, not just search" and "Writes are guarded"; drop "Your
server, your rules", whose content is now step 3.

**Trim** "Questions" (`:225-260`) to three entries — does it replace Overseerr
or Jellyseerr, can an assistant request on its own, does a language model see my
library. Delete "How is access controlled?" (goes stale with #44) and "Can I
self-host it?" (replaced by a single footer link to the README).

Net effect: after this edit the page contains no environment-variable name and
no mention of a token, which is what the new assertions encode.

### 2. `README.md` — the person who runs it

Fill six headings with real prose drawn only from code read in this clone, and
delete the seventh:

- `## Quick Start` (replaces `:86-87`) — container (`docker run` against the
  `Dockerfile`, port 8787, `/healthz`), standalone binary (the four artifacts
  from `release-binaries.yml`), and `seerrsense stdio`. The minimum settings are
  `SEERR_URL`, `SEERR_API_KEY` and `SEERRSENSE_AUTH_TOKEN`, the last mandatory in
  HTTP mode only, per `assertHttpConfig` (`src/core/config.ts:35-40`).
- `## MCP` (replaces `:121-122`) — `/mcp`, the four tools, the three scopes
  (`src/auth/config.ts:15-18`), the four discovery documents
  (`src/auth/routes.ts:255-271`), CIMD, and the `SEERRSENSE_OAUTH_CLIENTS`
  pre-registration form. Cross-links to `## Security Model` rather than
  restating it.
- Cloudflare Access and Nebius prose moves here as a short subsection immediately
  after the Configuration table (`README.md:89-119`), which already names all
  four variables — the prose lands next to its own reference material instead of
  on a marketing page.
- `## REST API` (replaces `:185-186`) — the four endpoints from
  `src/api/server.ts:285-360` plus the three `/api/v1/account/connection`
  methods, with the session-cookie-not-access-token distinction already argued at
  `README.md:131-135`.
- `## Architecture` (replaces `:188-189`) — the module map and the
  `TenantResolver` order (own → household → none,
  `src/providers/seerr/tenants.ts:44-102`), including the one-minute cache and
  why `forget()` is called on write (`src/api/account.ts:117`).
- `## Development` (replaces `:233-234`) — the six `package.json` scripts and the
  CI gate order in `.github/workflows/ci.yml`, including `TEST_DATABASE_URL`
  against the Postgres service container.
- `## Deployment` (replaces `:236-237`) — container build in CI, release-please
  for the version, tag push for the binaries.
- `## Roadmap` (`:239-240`) — **heading deleted**. There is no roadmap in the
  repo to describe, and an empty `*TBD*` reads worse than no section.

`## Whose Seerr` (`README.md:124-153`) is left alone here so it does not collide
with #44, which edits the same paragraphs.

### 3. `public/account.html` — one sentence

`public/account.html:42-44` currently promises SeerrSense will use the person's
instance "instead of the shared one". Once #44 restricts the household instance
to listed owners, a newcomer has no shared instance for it to be instead *of*.
Replace with: SeerrSense searches and requests on that instance. Nothing else on
that page changes.

### 4. `tests/landing.test.ts` — make it a regression guard

Append two cases inside the existing `describe("landing page")` block, using the
same `app.inject` shape as every case above them:

```ts
it("never instructs a token or an environment variable", async () => {
  const { payload } = await app.inject({ method: "GET", url: "/" });
  for (const forbidden of [
    "Authorization: Bearer", "Bearer &lt;your token&gt;", "bearer token",
    "CF_ACCESS_CLIENT_ID", "CF_ACCESS_CLIENT_SECRET",
    "NEBIUS_API_KEY", "SEERRSENSE_AUTH_TOKEN", "SEERR_API_KEY",
  ]) {
    expect(payload, forbidden).not.toContain(forbidden);
  }
});

it("gives the three steps and both client paths", async () => {
  const { payload } = await app.inject({ method: "GET", url: "/" });
  expect(payload).toContain('id="setup"');
  for (const needle of [
    "Add custom connector", "Developer mode",
    "Settings, then General, then API Key",
  ]) {
    expect(payload, needle).toContain(needle);
  }
  const [connector, signIn, seerr] = ["Add the connector", "Sign in with Google", "Attach your Seerr"]
    .map((h) => payload.indexOf(h));
  expect(connector).toBeGreaterThan(-1);
  expect(signIn).toBeGreaterThan(connector);
  expect(seerr).toBeGreaterThan(signIn);
});
```

The `indexOf` ordering assertion is the point: it pins the *sequence* the issue
argues for, not merely the presence of three strings. Both cases must be shown
failing against the unmodified page before the HTML is edited — that is the
verification the issue asks for and it is a task below, not an assumption.

Note the trap: the forbidden list must be checked against the *rendered* page,
and the page contains `seerr:read` / `seerr:request` chips. Those are scope
names, not environment variables, and are deliberately absent from the forbidden
list — `tests/landing.test.ts:32` already requires `seerr:request` to be present,
so a careless "no colon-separated identifiers" rule would contradict an existing
assertion.

A third test asserting the README has no `*TBD*` is deliberately **not** added:
`tests/` builds the Fastify app and asserts on HTTP payloads, and reading a repo
file from a vitest case would be the only filesystem test in the suite. README
completeness is a review-time check, listed in the DoD of the README task.

## Alternatives

**Fix the snippet instead of the section.** Replace `Bearer <your token>` with an
OAuth note and leave the rest of "Set it up" and "Connecting to Seerr" standing.
Cheapest possible diff and it removes the impossible instruction. Dropped: it
leaves the audience mix intact — the reader still meets `CF_ACCESS_CLIENT_ID` two
sections earlier and "an explicit list of addresses" two sections later, and #44
would immediately make the second one false again. It fixes the symptom the issue
titles and none of the three it argues.

**Move the operator material to a new `/self-hosting` page under `public/`.**
Keeps the landing page clean without touching the README. Dropped for two
reasons grounded in the code: `src/api/server.ts:165-172` deliberately declares
every public route by hand, so a new page means a new route plus a new
`PUBLIC_PREFIXES` entry plus new test coverage — a runtime change in a
documentation issue. And the material would then live in a third place while
`README.md:89-119` already documents the same variables, guaranteeing drift. The
README is the file a self-hoster opens first.

**Generate the landing page's setup section from the README at build time.**
Single source of truth, no drift. Dropped: there is no build step for `public/`
at all — the Dockerfile copies the directory verbatim (`Dockerfile:20-21`) and
`fastifyStatic` serves it from disk. Introducing a generator for one section
would add a build dependency, a CI check and a failure mode, all to keep two
paragraphs in sync that are written for different readers and should differ.

**Delete "What it adds" and "How a request travels" entirely**, as the issue
floats. Dropped for "How a request travels" specifically: `.flow-scroll` is
asserted at `tests/landing.test.ts:159-169`, so removing it forces an edit to an
existing, unrelated test — cost with no benefit to the issue's actual complaint.
"What it adds" is trimmed rather than deleted, since "Writes are guarded" is the
page's only explanation of why `request_media` is safe to grant.

## Platform impact

**Migrations.** None. No schema, no `src/` change, no environment variable added,
removed or renamed. `src/auth/store-pg.ts` and every table it owns are untouched.

**Backward compatibility.** The `#setup` anchor is preserved, so the top-bar link
(`public/index.html:46`) and external deep links keep working. The endpoint
element `#mcp-url` (`:70`), the `#copy-url` button (`:74`) and the
`.mcp-url-slot` class all survive; the slot simply moves from the deleted JSON
snippet into step 1, so `public/index.html:300-302` still has something to fill.
No REST or MCP surface is touched, so every existing client keeps working
byte-for-byte.

Removing the `Bearer` instruction does **not** disable the legacy token: it is
still accepted wherever `SEERRSENSE_LEGACY_TOKEN_ENABLED` is not `false`
(`src/auth/config.ts:66-68`), still documented in the Configuration table
(`README.md:93`), and still exercised by `tests/landing.test.ts:139-144` with
`SEERRSENSE_AUTH_TOKEN=secret123` from `package.json`. A self-hoster who uses it
loses nothing; the *hosted* page simply stops advertising something that is off
there.

**Resource impact.** The page shrinks by roughly 40 lines of HTML. No new asset,
no new font, no new request. `public/assets/tokens.css` is not touched, so
`npm run check:tokens` continues to pass unchanged.

**Risks and mitigations.**

- *Vendor menu paths go stale.* claude.ai and ChatGPT reorganise settings
  regularly and no test can detect it. Mitigation: an HTML comment next to the
  steps recording the 2026-09-09 verification date, so the next reader knows the
  age of the claim; a wrong-but-close menu path is still strictly better than
  today's impossible instruction.
- *Collision with #44.* Both issues edit documentation about who may sign in.
  This proposal deliberately does not touch `## Whose Seerr` (`README.md:124-153`)
  or `## Security Model` (`README.md:191-231`); it only *removes* the landing-page
  claims that #44 falsifies. Whichever lands second rebases; the overlap is
  confined to `README.md` prose with no code conflict. Note that
  `README.md:196-198` still describes the fail-closed allowlist and remains
  #44's to correct — flagged, not fixed here.
- *A forbidden-string test that is too broad.* Adding `"Bearer"` unqualified
  would collide with future legitimate prose and with nothing today; the list is
  therefore specific phrases plus exact variable names, and `seerr:read` /
  `seerr:request` are excluded because `tests/landing.test.ts:32` requires the
  latter to be present.
- *README grows long enough to bury the Configuration table.* Mitigation: the
  new sections are written short, each cross-linking to `## Security Model` and
  `## Whose Seerr` rather than restating them, and the Cloudflare/Nebius prose
  lands as a subsection of `## Configuration` rather than as a new top-level
  heading.
- *An unverified claim about the standalone binary.* `publicDir` resolves
  relative to the compiled module (`src/api/server.ts:173`) while the bun build
  compiles `src/index.ts` alone (`release-binaries.yml:26-32`), so whether a
  released binary serves `/` is not established in this clone. Mitigation: task 6
  verifies before `## Quick Start` claims it; until then the binary is documented
  for `seerrsense stdio` and left qualified for HTTP mode.

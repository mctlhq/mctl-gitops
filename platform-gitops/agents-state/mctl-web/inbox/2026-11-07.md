## Top-3 (for spec-writer)

### 1. nuxt-security-upgrade: Upgrade Nuxt 4.3.1 to 4.6.4 (with nitropack 2.13.6)
**Category:** security
**Impact:** 5
**Effort:** 3
**Rationale:** The architecture pins Nuxt 4.3.1, which falls inside the vulnerable range of CVE-2026-114131 (incorrect authorization, CVSS 6.5, fixed in 4.4.4). Nuxt 4.6.4 also fixes the later advisories (encoded-path bypass CVE-2026-119200, useHeadSafe server-island XSS CVE-2026-114133, getRouterParam mismatch CVE-2026-120309, NuxtLink XSS CVE-2026-114130, dev-server issues) plus three Nitro advisories. This is a minor-line bump within Nuxt 4, so it does not conflict with ADR 0001, which only requires tracking Nuxt releases. Runtime memory should be roughly neutral, but the spec should include a memory check before any rollout to `labs`, which is near its limit. ADR 0001 requires updating `context/current-version.md` and adding an ADR after the upgrade.
**Source:** https://github.com/nuxt/nuxt/releases/latest (v4.6.4, 2 Nov); CVE-2026-114131, CVE-2026-119200, CVE-2026-114133, CVE-2026-120309, CVE-2026-114130.

### 2. nuxt-4-6-behavior-audit: Audit app and Worker against Nuxt 4.6 behaviour changes
**Category:** security
**Impact:** 3
**Effort:** 2
**Rationale:** The 4.6.4 security release changes defaults: x-forwarded-proto is trusted only on opt-in, error details are limited to createError, and cached route rules apply only to GET/HEAD. SSR behind Kubernetes ingress and the Cloudflare Worker (OAuth callback, rate limiting) may depend on forwarded-proto for redirect or callback URL construction. The spec should verify these paths and set explicit opt-ins where needed. It should be delivered together with, or immediately after, proposal 1.
**Source:** nuxt v4.6.4 release notes (behaviour changes) in the github releases section.

### 3. sass-1-108-bump: Bump sass from 1.98.0 to 1.108.0 (skip 1.106.x)
**Category:** refactor
**Impact:** 2
**Effort:** 1
**Rationale:** The 1.98 to 1.108 jump is a low-risk toolchain update. 1.108.0 reverts the unintentional breaking changes from 1.106.0, so it is the first safe target after that regression. It is build-time only, with no runtime or `labs` memory impact. The spec should pin the version to avoid accidentally landing on 1.106.x or 1.107.x.
**Source:** https://github.com/sass/dart-sass/releases/latest (1.108.0, 6 Nov).

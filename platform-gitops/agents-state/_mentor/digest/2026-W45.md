## Top 5 Proposals Ready for Review

### 1. Pre-approval implementability and safe-slicing preflight for DevLoop
- **Service / slug:** mctl-agents / `issue-997-feat-devloop-pre-approval-implementabili` (proposed, updated 2026-11-03)
- **What:** A bounded, read-only, deterministic check that evaluates the exact digested proposal against the implementer's runner profile (one repo, USD 3 budget, 900 s timeout). It returns `feasible`, `needs_split`, `blocked_dependency` or `uncertain` before a human spends an approval.
- **Why:** Today a human approves a proposal the implementer then refuses (for example, one that needs a gitops companion write). The refusal leaves no commits and no PR, and the approval is wasted. Two currently stuck proposals (mctl-agents#993, mctl-api#866) show `no-commits` failures.
- **Impact 4 / Effort 3.**
- **Conflicts:** None incompatible. It pairs with issue-993 and issue-765 (same failure family) and should land first, since it reduces how often they are needed.

### 2. Strict registered-policy enforcement for action approvals (evidence-gated rollout)
- **Service / slug:** mctl-gitops / `issue-2141-rollout-governance-enable-strict-registe` (proposed)
- **What:** Adds `ACTION_APPROVAL_REQUIRE_REGISTERED_POLICY: "true"` to the production mctl-api Application. This follows an evidence gate that checks no live producer would be refused. The code shipped in mctl-api#766, which merged 2026-10-23.
- **Why:** Closes the gap where an executable approval could rest on an unknown policy rule. With strict mode on, create, decide and spend fail closed.
- **Impact 4 / Effort 1.** It is a one-line change plus an evidence step.
- **Conflicts:** None. **Caveat:** the observation window (`ACTION_APPROVAL_MAX_DECISION_AGE`) must have elapsed since 2026-10-23. It has, by date, but the evidence itself should be checked against live data. I could not do that here.

### 3. Agent-pod security hardening bundle (807 G3 / G4 / follow-up g)
- **Service / slugs:** mctl-gitops / `issue-2290` (readOnlyRootFilesystem, proposed), `issue-2289` (narrow ingress, needs-triage), `issue-2292` (pin the isolation auditor in CI, needs-triage)
- **What:** (a) a read-only root filesystem on all 7 agent steps with small `emptyDir` mounts and a CI check; (b) an MCTL-owned agent-pod label contract, so Vault, Backstage, shared-pg and intra-namespace ingress no longer admits agent pods; (c) a versioned-baseline CI gate using `tools/agent_isolation_audit.py`.
- **Why:** Agent pods run model-driven shells in the shared `argo-workflows` namespace, and the decision was to harden in place. This is the isolation boundary for that decision.
- **Impact 4 / Effort 3 for 2290; 3 for 2289 (NetworkPolicies are additive and need bidirectional proof); 2 for 2292.**
- **Conflicts / sequencing:** 2289 (PR #2306) and 2292 (PR #2312) are both in `needs-triage` with `merge-conflict`. Their work is done and approved, so a rebase is needed, not a rewrite. 2292 has a hard prerequisite, mctl-agents#921 (the auditor fix). 2290 and 2289 both edit the agent CWFTs and policies and will collide, so land them one at a time, 2290 first. 2292 should go last, so its baseline captures the hardened state.

### 4. Recover pre-accepted proposals without `approval_ref` (DevLoop deadlock fix)
- **Service / slug:** mctl-agents / `issue-978-fix-devloop-recover-pre-accepted-proposa` (proposed, 2026-11-02)
- **What:** When a proposal was accepted through the standalone approve path, the idempotent approve no-op never binds the DevLoop's `aar_` grant. The implementer then refuses with `execution not authorized`, and the loop stays Running with no PR. The fix binds a fresh human decision on the canonical grant. It does not weaken `execution_authorization` and does not treat legacy `approved_by` as authority.
- **Why:** A live deadlock with a reproduction (`mctlhq/.github#299`), and the failure message's remedy points the operator back at the failing path.
- **Impact 4 / Effort 2-3.**
- **Conflicts:** Touches the same approval surface as issue-993 (needs a fresh digest-bound approval) and issue-997. Review the three together, and land 978 first because it is a bug fix.

### 5. Stop loading project settings and MCP config from target-repo clones
- **Service / slug:** mctl-agents / `issue-868-fix-agents-stop-loading-project-settings` (proposed; amended 2026-10-28)
- **What:** Set `setting_sources=[]` and `strict_mcp_config` on all four target-clone SDK constructions, with tests that cover `.mcp.json`.
- **Why:** A probe showed that today a cloned repo's `SessionStart` hook and `.mcp.json` server both execute before any model request, and its `env` block is applied. The investigated repo can therefore run code in the agent. The severity was explicitly not downgraded.
- **Impact 5 / Effort 2.**
- **Conflicts:** None. It complements the isolation bundle in item 3 and should land before or alongside it.

## Platform Risks and Cross-Cutting Observations

1. **Merge-conflict parking is recurring.** issue-2289, issue-2292 (and in W38, issue-283) completed implementation and were approved, then stalled on `merge-conflict`. The shepherd cannot resolve conflicts. A conflict-rebase path or an operator-owned rebase routine would unblock the work cheaply.
2. **`no-commits` implementer failures** (issue-993, issue-866, and mctl-agents#746 behind issue-765) close an issue to the DevLoop permanently, and the approval is spent. Items 1 and 4 and issue-765 together address this. Until they land, expect more manual re-triggers.
3. **Approval-authority surface is being edited by several proposals at once** (978, 993, 997, 2141). Each is individually sound, but they should be reviewed in one pass for consistent semantics around digest binding and `aar_` grants.
4. **Shared `argo-workflows` namespace** carries both platform and agent workloads. The hardening in item 3 is the compensating control. Until it lands, an agent pod can reach Vault, Backstage and shared-pg through broad ingress selectors, and an agent step has a writable root filesystem.
5. **Incident proposal backlog:** roughly 236 `incident-*` proposals (mostly `accepted`) are open across mctl-gitops and mctl-agents. Some are duplicates of one root cause, for example `mctl-agents-image-tag-stale-post-slug-fix` (a needs-triage proposal dating from July). A bulk review and close pass is overdue. It also makes the proposals directories hard to scan.
6. **Unverified live state.** As noted above, I could not query the platform. Before acting on item 2 in particular, confirm that the mctl-api version running in production includes #766 and that there are no open approval-policy incidents.

## Top 5 Proposals Ready for Review

### 1. Stop agents-state pushes from starving the main merge queue
- **Service / slug:** mctl-gitops / `issue-2931-ci-gitops-agents-state-direct-pushes-sta` (updated 2026-11-22)
- **What:** (a) Detection: alert when the merge-queue head is rebuilt repeatedly. (b) Queue-aware deferral: an agents-state push waits, with a time limit, while a merge group is building, then writers push together right after a merge. Moving agents-state off `main` is recorded as a follow-up, not built here.
- **Why:** On 2026-11-22, 22 agent commits landed in 74 minutes. Each one outside the queue forced every merge group to rebuild. Queue head #2923 was rebuilt at least four times and never finished, and two other PRs got no merge group at all. Release PRs are affected, so this is a direct release-path blocker.
- **Impact 5 / Effort 3.**
- **Conflicts:** Touches the same `cwft-mctl-agents-*` commit-and-push step that the mctl-agents proposals touch. It also interacts with the bypass-key path P6 in the release-hold runbook, so confirm it does not widen that bypass. It is complementary to #2993 (both reduce CI contention) and should ship first, since it addresses the worse failure mode.

### 2. Relieve hosted-runner saturation (supersede stale runs, measure, then decide)
- **Service / slug:** mctl-gitops / `issue-2993-ci-hosted-runner-saturation-stalls-relea` (updated 2026-11-24)
- **What:** Add `concurrency` cancellation for PR-triggered checks and preview builds (extending #2935), clean up two runs queued since October and November, add a measurement script, and record an ADR on self-hosted runners versus a paid plan. Any self-hosted rollout is gated behind a tested fork-PR boundary.
- **Why:** The org is on the GitHub free plan with 20 shared concurrent jobs. On 2026-11-23 a release bump's merge-group check sat queued for 15 minutes behind 17 queued and 9 running mctl-gitops runs, 7 of them for superseded commits. Unrelated releases (mctl-telegram, mctl-alice) waited too.
- **Impact 4 / Effort 2.** The cheap steps are workflow-only.
- **Conflicts:** None incompatible. The self-hosted runner option is the risky part. It must not be enabled before the fork-PR boundary test passes. Review together with #2931 and mctl-api #1204 (theme A).

### 3. Deliver DevLoop approve and abandon signals reliably
- **Service / slug:** mctl-api / `issue-1162-fix-devloop-a-cancelled-request-after-th` (updated 2026-11-23)
- **What:** Detach the Temporal `approve` and `abandon` signals from the HTTP request context. Add a background redelivery path for grants that are `approved` but not `consumed`, a retry offer on the decide page in place of the dead end, and a metric plus logs for the partial state.
- **Why:** It already happened on 2026-11-22 (`dev-loop-mctlhq-.github-41`). The request was cancelled 35 ms after the decision was committed, so the workflow stayed parked forever and the link led to a dead end. An operator had to repair it by hand. It is the same bug class as the release-window settle fix (#1156).
- **Impact 4 / Effort 2.**
- **Conflicts:** None found. It touches the approval ledger and the decide page, so it must not create a second approval authority. The redelivery job must only act on grants already recorded as approved by a human. Related to the open W46/W47 approval-path items, but it does not overlap with them.

### 4. Investigator: catch triplets written outside `$PROPOSAL_DIR`, stop the blind fallback
- **Service / slug:** mctl-agents / `issue-1115-fix-investigator-a-successful-run-is-rep` (updated 2026-11-22), with the companion `issue-1114-fix-devloop-refuse-an-unknown-service-be` (updated 2026-11-22)
- **What (1115):** The investigator can write its proposal files one directory above the staging directory it was given. The run then reports success but "agent did not write" the files, the fallback account runs and fails, and nothing is published. The proposal detects the misplaced output, reports where it went, and stops the blind fallback. **What (1114):** Refuse a service that is not in `SERVICES` before any Argo workflow is created, give that refusal a distinct exit code and outcome (`unknown-service`) so the fallback is skipped, and stop attributing the failure to quota (429).
- **Why:** Both defects waste a run on the second account and give the operator a wrong diagnosis. 1115 also left a bogus proposal committed to main (see Platform risks).
- **Impact 3 / Effort 2 (1115), 2 (1114).**
- **Conflicts:** Both edit the investigate path and the `mctl-agents-investigate` ClusterWorkflowTemplate (which lives in mctl-gitops), so land them in one sequence to avoid a merge conflict. 1114 explicitly leaves the mctl-api direct-operation path and the CWFT to other repositories, so a follow-up is needed in each.

### 5. Bound the lint check and isolate gosec in mctl-api
- **Service / slug:** mctl-api / `issue-1204-ci-lint-gosec-on-internal-api-takes-10-m` (updated 2026-11-27)
- **What:** Give the `lint` job a hard `timeout-minutes`, move `gosec` into its own job with its own budget, and add per-rule timing so the owner can decide on exclusions. No rule is removed without an owner decision. `gosec` keeps running on PRs and main.
- **Why:** `gosec` takes about 600 s on `internal/api` and the timeout is 10 minutes. On 2026-11-27 the job hung twice for more than 25 minutes on #1201 and was cancelled by hand. Without `timeout-minutes` the default is 360 minutes, which also consumes the scarce shared runner slots from #2993.
- **Impact 3 / Effort 1.**
- **Conflicts:** None. A new job name changes the required-check set, so the branch-protection ruleset (`main-protection`) must be updated in step, otherwise PRs can block on a missing check.

## Platform Risks and Cross-Cutting Observations

1. **Agent pushes to main are the biggest delivery risk.** The same direct-push path that starves the merge queue (#2931) is the one that committed a bogus proposal. Fixing the queue and fixing the investigator (#1115) both touch the `cwft-mctl-agents-*` templates, so coordinate the two.
2. **Stray staging directory in the state tree.** `mctl-api/proposals/.staging-kptjmuhc/` (design.md, requirements.md, tasks.md, no `.status.yaml`) is still present. It is the misplaced output described in #1115. It is not a real proposal and should be removed. Digest tooling that globs the proposals directory will otherwise count it.
3. **Shared CI capacity is a single point of contention.** Hosted runners (20 jobs, free plan), the merge queue and the lint job (no timeout) all fail in the same way: release PRs wait behind unrelated work. Three proposals this week address it, so owners should treat them as one programme and not approve them in isolation.
4. **Silent partial states in approval flows.** #1162 shows an approval recorded but never delivered, with no log line. Together with the earlier release-window settle bug (#1156), this suggests a pattern: any "commit, then signal" sequence on a request context deserves an audit.
5. **Misleading error attribution.** #1114 shows deterministic configuration refusals being reported as quota exhaustion. This costs operator time and a second-account run each time.
6. **Public unauthenticated endpoints.** #1203 and #3042 both widen or depend on the anonymous edge. Review the rate-limit and fail-closed allowlist designs together.
7. **Large, long-running research proposals.** #1177, #549, #2929 and #1195 carry multi-revision review histories. Each authorizes no runtime change, so the risk is scope creep and review fatigue, not production risk. Ask owners for an explicit GO or NO-GO per stage.
8. **Unverified live state.** No mctl tools were available, so service versions, open incidents (including the mctl-api release hold carried over from W46/W47) and tenant limits (including `labs-preview` and `admins` quota alerts from W47) were not cross-checked. An operator should confirm them before approving anything that adds workloads or releases mctl-api.
9. **Carry-over:** the W45, W46 and W47 top items remain open, with no later status update. The state tree holds 274 `incident-*` proposals in mctl-gitops out of 414 proposals, so the backlog is still mostly auto-generated.

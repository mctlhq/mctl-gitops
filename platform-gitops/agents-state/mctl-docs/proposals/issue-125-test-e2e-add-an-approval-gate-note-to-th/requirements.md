# Note that agent-authored PR merges may require explicit human approval

## Context
Issue mctlhq/mctl-docs#125 is the live end-to-end test issue for mctlhq/mctl-agents#198 (durable human approval for the shepherd's merge). It asks for exactly one sentence of documentation stating that merges of agent-authored PRs in this repository may require an explicit human approval (an action-approval receipt) before the platform merges them. The issue asks for the README "or the most appropriate existing page"; this repository has no README, so the sentence goes on the page that already documents the shepherd's merge behavior.

The content change itself is small. What the test actually checks is the merge of the resulting PR, which must pass through WAITING_FOR_APPROVAL, a denied receipt, a head change that invalidates a receipt, and finally one approved merge of an exact head SHA. So the diff must stay minimal and must not touch anything else.

## User stories
- AS a contributor or operator reading docs.mctl.ai I WANT to know that the shepherd may wait for a human approval before merging an agent-authored PR SO THAT a PR sitting in a waiting state does not look like a stuck pipeline.
- AS the mctl-agents#198 E2E test operator I WANT a trivial, docs-only agent-authored PR SO THAT the approval-gated merge path can be exercised without risk to the product.

## Acceptance criteria (EARS)
- WHEN the change is applied THE SYSTEM SHALL contain exactly one new English sentence in `docs/mcp/tools-reference.md`, inside the `### mctl_trigger_shepherd` section, stating that merges of agent-authored PRs may require an explicit human approval (an action-approval receipt) before the platform merges them.
- WHEN the PR diff is inspected THE SYSTEM SHALL show changes to `docs/mcp/tools-reference.md` only, with no new files or pages.
- WHILE the change is in place THE SYSTEM SHALL leave `CHANGELOG.md`, `release-please-config.json`, `.release-please-manifest.json`, `package.json`, `bun.lock`, `.vitepress/` config and `.github/` workflows unmodified.
- WHEN `bun run build` (`generate:llms` followed by `vitepress build docs`) runs THE SYSTEM SHALL complete without errors.
- IF the sentence is rendered THEN THE SYSTEM SHALL contain no emoji and no new links.

## Out of scope
- Any edit to `CHANGELOG.md`. It is generated by release-please (`release-please-config.json`), and the issue forbids touching release configuration.
- Creating a README or any new page.
- Documenting how approval receipts work (API, MCP tools, denial or invalidation semantics).
- Committing a regenerated `docs/public/llms-full.txt`. The build step regenerates it.
- Running or verifying the approval-gate flow itself. That is the E2E operator's job and happens on the PR.

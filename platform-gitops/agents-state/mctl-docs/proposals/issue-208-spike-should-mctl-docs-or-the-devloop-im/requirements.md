# Spike: guidance and a check idea for PostgreSQL schema migrations that merge cleanly but conflict at apply time

## Context

Issue mctlhq/mctl-docs#208 (generated by the mctl-agents scout) asks whether mctl
should defend tenant apps against schema migrations that do not conflict in Git
but do conflict when they are applied to PostgreSQL. Two such migrations can come
from parallel agent or human pull requests. Typical shapes are two files with the
same sequence number, two migrations that each assume they run against the
pre-merge schema (for example both add `NOT NULL` columns, or one renames a column
the other indexes), or an ordering that differs between environments. The result
is a failed rollout or a schema that silently differs from what either PR author
tested. The issue lists one outcome: "Migration-conflict guidance and check idea".
The issue's non-goals rule out any implementation before the decision.

This matters on mctl because several tenant services on the shared CNPG cluster
own their schemas. They migrate in different ways: on start with an advisory
lock, through the chart's `dbInitJob` PostSync hook, or in app-specific steps.
DevLoop produces parallel PRs against the same repositories. Today
`docs/guides/databases.md` covers provisioning and credentials only and says
nothing about migrations. This proposal is a bounded spike. It runs one
falsifying experiment, writes a duplicate map and a recommendation, and, only if
the experiment confirms the gap, adds a short guidance section and a CI check
idea to the docs. Any DevLoop implementer check is filed as a follow-up and is
not built here.

## User stories

- AS a tenant developer with a PostgreSQL-backed service I WANT documented guidance on how parallel PRs can produce migration conflicts that Git does not flag SO THAT I can add a pre-merge check before a rollout fails.
- AS a platform maintainer I WANT a duplicate map and experiment evidence SO THAT I decide on docs vs. a DevLoop implementer check from measurements, not vendor claims.
- AS a DevLoop operator I WANT any implementer-side check proposed as a separate follow-up in its owning repository SO THAT no agent authority or rollout changes ride on a docs spike.

## Acceptance criteria (EARS)

- WHEN the spike starts THE SYSTEM SHALL produce a duplicate map that classifies each Related issue (mctl-gitops#1044, mctl-agents#918, mctl-gitops#2506) and every existing docs page that mentions databases or migrations as duplicate, adjacent, or unrelated, with a one-line reason each.
- WHEN the experiment runs THE SYSTEM SHALL use a scratch repository with two branches off one base, each adding one migration, that merge with no Git conflict, and apply the merged result to an ephemeral `postgres:17` instance (the same major version as the chart's `job-db-init.yaml` image).
- WHEN the experiment runs THE SYSTEM SHALL cover at least these three scenarios: (a) duplicate sequence number or version, (b) semantically conflicting DDL that applies in one order and fails in the other, (c) a merge that applies without error but leaves a schema different from either branch's tested schema.
- WHEN each scenario is measured THE SYSTEM SHALL record the baseline (no check) and the candidate (pre-merge apply-from-merge-result check) for success, wall-clock latency, CI cost (minutes), and reliability (false positives and false negatives over repeated runs), and SHALL record any value it did not measure as `unknown`, never as zero.
- IF the experiment shows that none of the scenarios goes undetected by the baseline THEN THE SYSTEM SHALL recommend "no change" and SHALL NOT edit any published docs page.
- IF the experiment confirms at least one undetected scenario THEN THE SYSTEM SHALL add a "Schema migrations and parallel PRs" section to `docs/guides/databases.md` and a "Pre-merge migration check (optional)" snippet to `docs/guides/scaffolding.md`, written in the same style as the existing "Pre-merge docker build (recommended)" section.
- WHILE the docs guidance is published THE SYSTEM SHALL describe the check as opt-in tenant CI and SHALL NOT claim that mctl, the `deploy-service` operation, or DevLoop runs it.
- WHEN the spike concludes THE SYSTEM SHALL record exactly one recommendation from the issue's Outcomes in `context/plans/migration-conflict-spike.md`, and SHALL list follow-ups (for example a mctl-agents issue for an implementer-side check) as issue drafts, not as implemented code.
- WHILE this proposal is executed THE SYSTEM SHALL NOT change mctl-gitops charts, tenant values, DevLoop/agent permissions, approval gates, or rollout behaviour.
- WHEN docs pages change THE SYSTEM SHALL keep `bun run build` (tests, `generate:llms`, VitePress build) passing.

## Out of scope

- Implementing a migration check in the DevLoop implementer, shepherd, or any mctl-agents code.
- Changing the base-service chart (`dbInitJob`, PostSync hooks) or any tenant `values.yaml`.
- Choosing or mandating a migration tool (Flyway, golang-migrate, Prisma, Alembic, sqitch) for tenants.
- Running experiments against the shared CNPG cluster or any tenant database.
- New epics, runtimes, or platform capabilities added only for feature parity.

## Open questions

- Who owns an implementer-side check if the experiment justifies one: mctl-agents (implementer prompt or validator, near mctl-agents#918's deterministic-validation work) or tenant CI only? This proposal records it as a follow-up and does not decide it.
- The issue's Source link (https://postgr.es/p/9Bm) could not be dereferenced in this run. The scenarios above come from known PostgreSQL migration failure modes, not from that article.
- How many deployed tenant services actually run versioned migration files, as opposed to ORM auto-sync or advisory-locked migrate-on-start? Gitops values only show the deploy wiring, not the app's migration tool. The duplicate map should record this as "unknown per service" where it is not visible.
- Whether a "check idea" should also be offered as a reusable GitHub Actions snippet maintained elsewhere (for example in `.github`) is left to the follow-up.

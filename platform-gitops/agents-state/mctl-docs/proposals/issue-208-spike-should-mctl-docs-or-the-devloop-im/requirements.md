## Problem

Two pull requests (from agents or people) can each add a migration, merge with no Git conflict, and still
fail or produce an unintended schema when applied to PostgreSQL. `docs/guides/databases.md` today has the
headings "Database Provisioning", "Provision a Database", "Configuration" and "Supported Databases". It
covers provisioning and `DB_*` variables and says nothing about migrations.

## User stories

- AS a tenant developer with a PostgreSQL-backed service I WANT clear guidance on migration conflicts that Git
  does not flag SO THAT I can reduce rollout failures.
- AS a platform maintainer I WANT the guidance to state clearly what the platform does and does not do SO
  THAT nobody assumes mctl orders, checks or rolls back tenant schemas.

## Acceptance criteria (EARS)

- WHEN the guide is written THE SYSTEM SHALL explain a Git-clean migration conflict: unique versions,
  ordering, and why two migrations that each assumed the pre-merge schema can pass separately and fail or
  diverge together.
- WHEN the guide describes compatibility THE SYSTEM SHALL explain old-app/new-schema and new-app/old-schema
  overlap during a rollout and recommend expand/contract (additive change first, switch, remove later).
- WHEN the guide describes verification THE SYSTEM SHALL separate (a) deploying onto an empty database from
  (b) upgrading the supported previous schema with synthetic data, and SHALL state that (a) does not prove
  (b).
- WHEN the guide describes recovery THE SYSTEM SHALL state that rolling back the application version does
  not roll back the database, and that recovery is a coordinated forward fix or a separately verified
  schema/data rollback.
- WHEN the guide describes a merge-result check THE SYSTEM SHALL present it as an opt-in idea for tenant CI:
  what it evaluates (the merged result, not each branch alone), how it goes stale (the merge result is only as
  fresh as its last run unless the branch is up to date or a merge queue is used), and its limits.
- WHEN the guide discusses conflicts THE SYSTEM SHALL distinguish a real conflict from a legitimate merge of
  independent changes, and SHALL say that a schema diff is not an oracle by itself: expected semantics and
  the procedure for refreshing any schema snapshot need review.
- WHEN the guide names unmeasured parameters THE SYSTEM SHALL list them as unmeasured: conflict coverage,
  latency, CI cost, false-positive rate and the per-service migration tool.
- WHILE the guide is published THE SYSTEM SHALL NOT claim that mctl, `deploy-service` or DevLoop runs,
  enforces or orders migrations, and SHALL NOT present the idea as measured or deployed.
- WHILE this proposal is executed THE SYSTEM SHALL NOT add a workflow, runner, SQL, reusable action, CI
  enforcement, migration-tool mandate, cluster or tenant access, install, release, tag or deploy.

## Out of scope

- Any PostgreSQL, Docker or scratch-repository experiment; Actions jobs; repeated scenario runs.
- Implementing a check in DevLoop or mctl-agents; changes to charts, `dbInitJob` or tenant values.
- Choosing a migration tool for tenants.
- Claims of coverage of all conflicts, latency, savings or false-positive rate.

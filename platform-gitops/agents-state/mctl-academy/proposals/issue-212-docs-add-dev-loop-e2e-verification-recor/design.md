# Design: issue-212-docs-add-dev-loop-e2e-verification-recor

## Current state

`mctl-academy` today has no `docs/` directory (confirmed: `find . -iname docs
-maxdepth 2` returns nothing in the clone). Repository-level documentation
lives as top-level Markdown files: `README.md`, `PLAN.md`, `CONTENT-POLICY.md`,
`SOURCES.md`, `LEGAL.md`, `CONTRIBUTING.md`, `PRIVACY.md`, `SECURITY.md`,
`LLMS.md`, plus `client/README.md`. None of these existing files documents the
mctl-agents dev-loop's *operational history* against this specific repo —
`PLAN.md` section 5 ("Agents and PR flow (Temporal dev-loop)", lines 163-246)
documents the pipeline's *design and mechanics* (the CWFT chain
`investigate` -> `wait_condition(approved)` -> `implement`, the two-step
approval via Temporal signal + `.status.yaml` flip, registration in `SERVICES`
/ `NON_ROTATING_SERVICES`), but records no verified runs.

Content in this repo is governed by `content/schemas/`, `scripts/
validate-content.mjs`, and the bundle builder (`scripts/build-content-bundle.
mjs`) per `CLAUDE.md`'s "The gate" section — but that machinery applies to
`content/{questions,lessons,sources}/`, i.e. exam-item content with
`course_id`, evidence citations, and publication status. `docs/dev-loop-e2e.md`
is operational/process documentation, not exam content: it carries no
`course_id`, is not a question/lesson/source, and is explicitly out of the
schema/lint/bundle pipeline's domain. No existing lint, test, or CI workflow
(`ci.yml`, `content-evidence.yml`, `e2e.yml`, `claude-review.yml`, etc. under
`.github/workflows/`) references a `docs/` path, so adding one is additive
and touches no existing gate.

`CONTRIBUTING.md` and `CLAUDE.md` both state conventions this file must
follow: conventional commits (`docs:` prefix fits — this is a pure
documentation change), branch naming not starting with `_`, merge commits
(never squash), English only, no emoji, no `Co-Authored-By` trailers.

## Proposed solution

Add exactly one new file, `docs/dev-loop-e2e.md`, containing:

1. A short intro paragraph naming the dev-loop's stages
   (issue -> spec proposal -> human approval -> PR) and linking to
   `mctlhq/mctl-agents` ADR-006, mirroring (without duplicating) the fuller
   mechanics already written in `PLAN.md` section 5. The paragraph is
   deliberately generic/pipeline-level rather than mctl-academy-specific, so
   it stays accurate as the pipeline evolves — the specifics belong to
   `mctl-agents`, this file only needs to orient a reader before the table.
2. A `## Verified runs` heading followed by a Markdown table with columns
   `Date | Issue | Pipeline version`, and one row for this run:
   `2026-08-29 | mctlhq/mctl-academy#212 | mctl-agents 1.30.0`.

This is the minimal change that satisfies the issue: a new, isolated file,
appendable (each future verified E2E run adds one more table row, no
restructuring), and it creates a `docs/` directory precedent that does not
yet exist in this repo — chosen over stuffing the record into an existing
file (see Alternatives) precisely because the issue asks for a "living
record file" whose only job is this table, and it should not entangle with
files that have their own purpose and their own review gate (e.g. `PLAN.md`
is a "canonical MVP plan", not a running log).

No code, schema, CI workflow, or existing documentation file changes. No
`content/` files are touched, so `npm run lint:content` / `npm run
test:content` are unaffected and need not be re-run for this change to be
safe. The file is plain Markdown with no front matter, no JSON Schema
binding, and no client/server code reads it — it is documentation for
humans and future agents reading the repository, not a build input.

## Alternatives

1. **Append to `PLAN.md`.** Rejected: `PLAN.md` is explicitly "the canonical
   MVP plan" — a point-in-time design document with its own "Changes from
   the draft" changelog convention. Mixing a running, append-only
   verification log into a document that otherwise describes fixed decisions
   would make both harder to read and blur what "changing PLAN.md" means for
   review purposes.
2. **Add a `CHANGELOG.md` entry.** Rejected: `CHANGELOG.md` in this repo is
   generated by `release-please` (see `.release-please-manifest.json`,
   `release-please-config.json`, `.github/workflows/release-please.yml`) —
   it is derived from conventional-commit messages on merge, not
   hand-authored. Adding a manual entry would fight the automation and is
   not what the issue asks for (it explicitly wants a docs file with a
   table, not a changelog line).
3. **Put the record under `content/`.** Rejected outright: `content/` is
   schema-governed exam material (`course_id`, `authored.by`, evidence
   citations per `CONTENT-POLICY.md`/`SOURCES.md`). A pipeline-verification
   record is not exam content and must not enter a directory whose lint
   (`scripts/validate-content.mjs`) and bundle builder
   (`scripts/build-content-bundle.mjs`) assume every file is a question,
   lesson, or source.
4. **No new directory; place the file at repo root
   (`DEV-LOOP-E2E.md`).** Considered and dropped in favor of the issue's
   explicit path (`docs/dev-loop-e2e.md`): the issue names the path
   directly, and a `docs/` subdirectory is a reasonable, low-cost precedent
   for future non-root documentation without cluttering the root alongside
   the existing policy/legal files.

## Platform impact

- **Migrations:** none. No database, schema, or content-bundle change.
- **Backward compatibility:** fully additive; no existing file, path, import,
  or build step is touched. `client/src/content-bundle.json` and
  `client/src/course-catalog.json` regeneration (per `CLAUDE.md`) is
  unaffected since no `content/` file changes.
- **Resource impact:** negligible — one small Markdown file, no runtime
  component, no deploy required (this is not served by the Hono API or the
  Vite client; it is a repository doc, not part of `client/` or `server/`).
- **CI impact:** none of the existing workflows
  (`ci.yml`, `content-evidence.yml`, `e2e.yml`, `source-drift.yml`,
  `capture-sources.yml`, `claude-review.yml`, `context7-reindex.yml`,
  `release-please.yml`, `agy-review.yml`) reference `docs/`; a docs-only PR
  should pass all of them without modification. Per `CLAUDE.md`'s "Review
  gates" section, this is "everything else" (not content), so it goes
  through `claude-review.yml`'s normal automated review, gated on no
  unaddressed P1/P2 — consistent with a docs-only change carrying low risk.
- **Risks + mitigations:**
  - *Risk:* the ADR-006 link target cannot be confirmed from this read-only
    `mctl-academy` clone (no access to `mctlhq/mctl-agents`). *Mitigation:*
    ship a best-effort link and flag it explicitly in `## Open questions`
    (requirements.md) and in the PR for human-reviewer confirmation; this is
    a docs-content accuracy risk, not a functional/security risk, and does
    not block merge of the file's structure.
  - *Risk:* future automation (if ever added) forgets the file exists and
    duplicates verification records elsewhere. *Mitigation:* out of scope
    here; noted as a natural follow-up but not required by this issue.

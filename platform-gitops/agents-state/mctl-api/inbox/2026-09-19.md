## Top-3 (for spec-writer)

### 1. mcp-go-upgrade-v2: Escalate target to mcp-go >=v0.56.0 for CVE-2026-81092 (missing Host header validation / DNS rebinding)
**Category:** security
**Impact:** 5
**Effort:** 3
**Rationale:** CVE-2026-81092 (CVSS 6.8) is genuinely new signal (published 2026-08-27, first seen this cycle) and directly hits `mark3labs/mcp-go`, our sole MCP library per ADR-0001. `StreamableHTTPServer.ServeHTTP`/`SSEServer.ServeHTTP` accept any Host header on loopback-bound listeners, so a browser-controlled DNS name could reach `api.mctl.ai/mcp` and invoke tools (13 of the 24 tools are write tools) — a public, high-blast-radius attack surface. No existing proposal targets a version that includes this fix: the highest-version unmerged proposal (`mcp-go-upgrade-v2`) only targets v0.54.0, below the v0.56.0 fix. Recommend escalating that proposal's target to >=v0.56.0 (or straight to the newly-released v1.1.0 stable) rather than opening a new slug, and re-running the mandatory MCP Inspector validation gate from ADR-0001. This does not touch tenant `labs` (mctl-api runs only in `admins`).
**Source:** inbox CVE section, "mark3labs/mcp-go — CVE-2026-81092"; existing `proposals/mcp-go-upgrade-v2/` (currently targets v0.54.0).

### 2. pgx-critical-memory-safety-cve: Merge-priority escalation — critical pgx memory-safety CVEs still unpatched, gap now 3 minors behind
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** CVE-2026-33815/CVE-2026-33816 (CVSS 9.8, memory safety) and CVE-2026-41889 (SQL injection) remain unresolved against our pinned pgx/v5 5.8, and the upstream gap has now grown to three minor versions past the 5.9.0/5.9.2 fix (latest is 5.11.0, released this cycle). This is not new-scope work — `proposals/pgx-critical-memory-safety-cve` already targets the correct fix version (5.9.2) and explicitly supersedes the older `pgx-upgrade-v592` — but it is the single highest-severity item in the entire backlog (touches identity and audit-log tables) and remains stuck unmerged alongside five other duplicate pgx proposals. Recommend the spec-writer prioritize merging this exact proposal and formally closing the five duplicates (`pgx-upgrade-v592`, `pgx-security-upgrade`, `pgx-sql-injection-fix`, `pgx-sqli-patch`, `pgx-cve-sql-injection`) as superseded, rather than drafting yet another pgx slug. No `labs` impact (pgx is used only by mctl-api in `admins`).
**Source:** inbox CVE section, "jackc/pgx — CVE-2026-33815/33816" and "CVE-2026-41889"; existing `proposals/pgx-critical-memory-safety-cve/`.

### 3. mctl-self-observability-gap: mctl-api's own status/config/log MCP tools cannot introspect mctl-api itself
**Category:** refactor
**Impact:** 3
**Effort:** 2
**Rationale:** Two consecutive research cycles (2026-08-22 and 2026-09-19) confirm `mctl_get_service_config(team=admins, service=mctl-api)` errors with "service not found: admins/mctl-api", `mctl_get_service_logs` returns zero lines for mctl-api over a 24h window, and `mctl_get_service_status` returns a null `service` field (no pod-level CPU/memory/replica data). Since these are mctl-api's own MCP tools (per architecture.md, mctl-api hosts the 24-tool MCP server including `get_service_status`/`get_tenant_metrics`), this is a bug in mctl-api's own service-catalog lookup or logging pipeline, not a third-party dependency issue — it blocks operators (and this very daily research pipeline) from confirming the deployed image tag against `current-version.md` (last updated 2026-04-27, unverified for 5 months) or diagnosing resource usage ahead of the pgx/mcp-go upgrades above. No existing proposal in the backlog addresses this. Low effort relative to impact: likely a catalog-key mismatch (`admins/mctl-api` vs. actual registered name) plus a Loki label/stream check.
**Source:** inbox "Source: mctl metrics" section, all three bullets (service config error, empty logs, null service status field).

## Current state

- `internal/bridge/` implements the command bridge (mctl-api#962, documented in `docs/bridge.md`): a Postgres command outbox, a claim endpoint with leases (`lease_epoch`, a rotating private `lease_nonce`), an exactly-once result CAS, and `IssueWritePermit` in `internal/bridge/permit.go`. The bridge is dark: `MCTL_BRIDGE_ENABLED` gates it in `cmd/api/main.go`.
- `WriteFence` (`internal/bridge/permit.go`) is the transaction-compatible hook. At `ceac9ed` the only implementation is `refusingFence`; the real fence is #989 `receipt.Fence`, whose `PreLock` and `Check` run inside `IssueWritePermit` under the #957 §6b lock order (#985 §7.2). Existing store tests use `allowFence` (`internal/bridge/store_pg_test.go:33`); this slice never does.
- Effect states are `none`, `permitted`, `succeeded`, `failed`, `not_performed` and `unknown` (`internal/bridge/store.go`). A reclaim or an expiry turns `permitted` into `unknown`. That is the existing mechanism the "ambiguous effect gives unknown" criterion depends on.
- Existing PG evidence (`TestPGReclaimAfterPermitMarksEffectUnknown`, `TestPGWritePermit`, `TestPGClaimResultReplayAndTenancy`, `TestPGExpiredLeasedPermitIsUnknownAndAudited`) uses the superuser `pgStore` helper and covers one transition each. None chains the flow, uses the real fence or the role split, or forces a race order.
- The v1alpha1 schemas are vendored from mctl-agents#1045 in `internal/bridge/schema/` with `PROVENANCE` and `TestVendoredSchemasMatchProvenance`. The Glovo write command and the read kinds are the `bridge.mctl.ai/v1alpha2` files of mctl-agents#1059, vendored by #986 (task 1) under `internal/bridge/schema/v1alpha2/` with `SHA256SUMS` (`command-place-order-fake`, `read-command`, `read-result`, `claim-response`; the `place_order_fake` result document stays v1alpha1). The write command is therefore validated against the v1alpha2 file and never against `internal/bridge/schema/*.schema.json` (v1alpha1 only). #985 vendors no bridge schema, and enqueues with `WireVersion: bridge.WireV1alpha2`. #985 owns `internal/glovo/control/contract/*.json` and its `SHA256SUMS`; #957 owns `internal/glovojoin/contract/`.
- #957 ships the join routes, `glovo.control_starts` with its dispatcher (§6c) and a harness (`internal/glovojoin/harness_test.go`, build tag `glovojoin_fixture`, §8) that builds the real `api.NewRouter` over the real stores. This slice extends that harness; it does not build a second one.
- CI (`.github/workflows/validate.yml`) runs `go test -p 1 ./...` against a `postgres:16` service with the superuser URL `TEST_DATABASE_URL`, and a separate "bridge PostgreSQL tests (fail-closed evidence)" step that runs `-run 'TestPG' ./internal/bridge/`, fails on any `--- SKIP` and requires named `--- PASS` lines. PG tests skip locally without `TEST_DATABASE_URL`.
- `e2e/e2e_test.go` sits behind `//go:build e2e` and targets a live deployment. It is unsuitable here because the bridge is dark in every deployment.
- The clone at `ceac9ed` contains none of #988, #989, #985, #986, #957's join routes or the #1059 files; `git log` ends at #984.

Deployed state checked:
- `mctl_get_service_config(team=admins, service=mctl-api)` returned "service not found: admins/mctl-api". The tenant/service binding of mctl-api was not observed.
- `$MCTL_GITOPS_ROOT` `services/` holds tenants `admins`, `karabu`, `labs` and `namax66`. `services/admins/` lists no `mctl-api` directory, so the deployed values (including whether `MCTL_BRIDGE_ENABLED` is set) were not observed. This change is test-only and needs no deployed flag, but the gap is recorded under Open questions.

## Proposed solution

Add a test-only package, `internal/glovo/contract`, built under the `glovojoin_fixture` tag, with a PG-backed suite. It adds no production code path. The helpers live in `_test.go` files, plus a loopback-only fake provider in `internal/glovo/contract/fakeprovider` that no `cmd/` imports.

1. **Harness and roles (F2).** `TestMain` connects to `TEST_DATABASE_URL` as the superuser, creates a throwaway database, and creates `glovo_migrator`, `glovo_runtime` and a work-items role if absent (default names; the role name is configuration, #957 §6d.1 R1). It runs the `ApplySchema` chain as the migrator in the §6d.1 order, opens one pool as `glovo_runtime`, builds the bridge store with `bridge.NewRuntimeStore` and the other stores with their constructors, and requires `control.ProveOneDatabase` and `receipt.Ready` to return nil before any test starts. A test that runs against a database where this has not passed fails at once. The database is dropped at the end, so no other package's rows are touched and no bridge table owned by `NewStore` under another role blocks `ApplySchema` (OPEN-957-6). The gates are opened only through the fixture-tag seam below; the release build must not contain them. It also requires `Store.WireVersionsEnabled()` (#986 §2) to be true and the fake provider's `MCTL_BRIDGE_PROVIDERS` entry to declare `supported_versions` with v1alpha2 (the list must also contain v1alpha1, #986 §2; `Caller.Versions`, #986 §2; the real provider's value is the activation precondition OPEN-986-6, owned by the gitops P1 activation issue, not by this suite): otherwise `Enqueue` refuses with `ErrReadUnavailable` and dispatch answers `not_ready` (#985 §5 step 11).
   *Fixture seam (the names are #985 §7.4 and #957 §8; this slice defines none).* One build tag, `glovojoin_fixture`. In `internal/glovo`: `gate_release.go` / `gate_fixture.go` (`const controlGateOpen`, backing `glovo.ControlDefault`; it lives in this package because an unexported const cannot back a var in another one). In `internal/glovo/control`: `ttl_release.go` / `ttl_fixture.go` (`DispatchCommandTTL`, and in the fixture file `SetFixtureDispatchCommandTTL(d)`, called before the router starts). In `internal/glovojoin`: `ttl_release.go` / `ttl_fixture.go` with `SetFixtureGlovoApprovalTTL(d)`. Connection expiry needs no override: it is driven with short real durations (`ActivateInput.ExpiresIn` of a few seconds, or a direct `UPDATE glovo_connections SET expires_at = clock_timestamp() + interval '2 seconds'` in the throwaway database, then a wait); there is no injected clock, because every expiry decision is the database's `clock_timestamp()`. The tag opens only the const: the `MCTL_GLOVO_CONTROL_ENABLED` flag, the `ProveOneDatabase` proof, #959 `Ready()`, `MembershipRevocationWired()`, the revocation hook and `receipt.Ready` (the #985 §7.3 items 2 to 6) stay real, and a run that stubs any of them is not a pass. The release-build checks are #985 T29 (`TestControlGateClosedInReleaseBuild`, `TestFixtureFilesAreTagged`) and #957 T13 (`TestGlovoApprovalTTLSeam`), required by name in the CI step.
   `TestPGGlovoContractNotReady` repeats the startup with the runtime pool opened as the superuser, then as an owning role: the proof fails, the routes answer `not_ready`, the fence stays `refusingFence` and the fake provider records zero writes.
2. **Fake provider.** An in-process `httptest` server bound to 127.0.0.1 acts as the provider worker through the real bridge routes: it claims declaring `bridge.mctl.ai/v1alpha2`, serves the read kinds with payloads valid under the #1059 read-result schema (vendored by #986), takes the write permit, performs a synthetic effect in memory keyed by `command_id` (idempotent, with read-back) and posts the result in the shape that #1059 `command-place-order-fake` and the #986 vendored copy define (a v1alpha2 command, a v1alpha1 result document). It exposes `Writes(commandID) int` and fault knobs: `AmbiguousEffect`, `DropResultPost`, `CrashAfterPermit` (discard in-memory state and stop), `DuplicateResultPost` and `EndWithoutPermit` (post a terminal `approval_refused` result for the command without taking the permit). A dial guard is installed on the `http.Transport` of every client the harness builds and on `http.DefaultTransport`, and fails the test on a non-loopback dial. Its own unit tests cover each knob and the guard, and run in the CI step.
3. **Control-worker stand-in.** The mctl-agents#1044 workflow is not run here. A test client plays its role against the real #985 routes with the fixture-tag control-worker principal: it takes the stored `glovo.control_starts.input`, validates it against the vendored `glovo-control-input.v1alpha1.json` (#957 §6c), polls `read_approval`, calls dispatch with `approval_ref` and `fingerprint`, and polls `read_command_result`. The #957 §6c dispatcher runs against a recording starter that returns a run id; the bridge signal dispatcher runs against a recording `BridgeSignaler`.
4. **Flow test (F1).** `TestPGGlovoContractHappyPath`:
   - reads through the real #986 client and the fake provider: `orders:list`, `previews`, `basket`;
   - `orders:prepare`; asserts one `glovo.control_starts` row, one pending `aar_`, zero `place_order_fake` commands and zero fake-provider writes;
   - the owner decides the `aar_` through the owner decision route; a different member and a non-owner admin are refused (#989 T2 covers the matrix, this is the in-flow check);
   - the dispatcher starts the workflow with the id of #957 §6c; the stand-in dispatches; the provider claims, takes the permit, writes once and posts its result;
   - `read_command_result` returns the #985 §2a body; `GET /orders/{order_id}` returns the #957 §3a row for a placed order;
   - `read_command_result` is the call that runs `reconcileOrder` (#985 §2a), so after the first read the stored order is `closed` and the `GET /orders/{order_id}` row is the one #957 §3a gives for the pair, `placed`;
   - asserts the invariants of requirements.md (one permit row, `effect_state=succeeded`, `aar_` consumed, order closed, `run_id` equals the started run, the signal went to the stored workflow and run with the read-back digest).
   A static test (`TestGlovoContractNoShortcuts`) scans the package for `allowFence`, `.Enqueue(` outside the #985 code path, and SQL text that writes `action_approval_requests` or `glovo.orders`, and is shown red by adding one of each.
5. **Races (F3), deterministic by observed locks, not by sleeps.** The permit takes L1 shared, L2 shared, L3, L4 and then L5 (#957 §6b, #985 §7.2); the #959 enders take L1, L2 exclusive and then `CancelOpenForConnections` on L5.
   - *Revoke wins:* the real revoker (each of `Revoke`, `RevokeInstall`, `Reconnect` with `superseded`) is paused after it holds L2 exclusive and before it commits. The pause is a wrapper around the real hook, installed through the public `glovo.WithRevocationHook(...)` option: it signals that it is paused, waits for a release, then calls the real `bridge.CancelOpenForConnections` with the same arguments. No other seam is added to #959. `IssueWritePermit` starts in a goroutine and is observed waiting on that advisory lock in `pg_locks` (`granted = false`, polled). The revoker commits, and the test asserts the owner's refusal (#985 T13, #989 T11), zero fake writes, `effect_state=none`, no permit row, an audited refusal, and the `aar_` state that #985 §6 defines. The same test with a #985 cancel in the revoker's place.
   - *Write wins:* the permit holds the locks and a revoker is observed waiting. The permit commits and the fake provider writes once; the revoker then proceeds and the command ends `unknown` (#985 §7.2). Every later permit, reclaim or duplicate result is refused, and the test asserts exactly one write and one audit record.
   - *Timeouts:* the connection `expires_at` and the `aar_` `expires_at` or `fresh_until` pass between dispatch and permit, and the permit is refused with zero writes (#985 T24, #989 T7). The TTLs are shortened only through `SetFixtureDispatchCommandTTL` and `SetFixtureGlovoApprovalTTL`, and the connection expiry through short real durations, as in item 1 (OPEN-985-13, -14).
   - A bounded context fails the test instead of hanging. Each test asserts its non-vacuity precondition (the permit goroutine was seen waiting).
6. **Result to order** (`TestPGGlovoContractResultToOrder`; the table itself is owned by #985 §2a and proved over all 30 pairs by #985 T27 `TestReconcileOrderTable` and #957 T6, both delegated by name). This suite proves the chain through the real handlers for four pairs and asserts for each that the order is never left `dispatched` behind a terminal command and that `GET /orders/{order_id}` agrees with the stored order after the transition: (a) `completed` and `succeeded` (the happy path) is `closed`, wire `placed`; (b) `EndWithoutPermit` gives a `completed` command with effect `none` or `not_performed`, so the order is `closed`, the wire state is `failed` and the `aar_` is `unknown` (the receipt could never be spent; #989 §4, `MarkGlovoApprovalUnknownTx`), with zero writes; (c) a #985 cancel before the claim, and an expiry through `SetFixtureDispatchCommandTTL` of a command that no claimer takes before its TTL (the state a command is in when the provider does not declare v1alpha2), give `cancelled` with effect `none` and the order `cancelled`, wire `cancelled`; (d) a cancel after the permit gives an order `unknown`, never `cancelled`. A read that cannot be completed (a pair outside the table, forced by a harness `UPDATE` of that command's `status` and `effect_state` columns in the throwaway database; the shortcut scan of item 4 forbids writes to `action_approval_requests` and `glovo.orders` only, never to `bridge_commands`) answers 503 `unavailable` on `read_command_result` and on `cancel`, with no state body and the transaction rolled back (#985 §2b); the facade `GET` answers 503 as well (#957 §3a). Provider version gating is delegated by name: a `[v1alpha1]` provider never receives the v1alpha2 command (#986 T4f, T4h, T7c) and the real provider code refuses what it does not support (mctl-telegram#1262 T26, T27).
7. **Ambiguity and recovery** (`TestPGGlovoContractUnknown*`): an ambiguous provider reply; a crash after the permit followed by lease expiry and reclaim under `lease_epoch+1`; a lost result post followed by the `Expirer` sweep; and a stale-token result from the old holder (`lease_stale`). Each asserts `effect_state=unknown`, no second permit (`permit_already_issued`) and `Writes==1` (0 when the crash precedes the effect).
8. **Exactly once** (`TestPGGlovoContractExactlyOnce`): N concurrent dispatches and N concurrent claimers, a repeated dispatch (same `cmd_`, `Idempotent-Replayed`, #985 T1), a second `aar_` on the same order (`approval_replayed`), duplicate result posts (replay gives `replayed:true`, a different digest gives `result_conflict`). One effect per approved intent.
9. **Isolation** (`TestPGGlovoContractIsolation`), one table per surface (F5): {tenant A, tenant B} x {principal 1, principal 2} over (a) the bridge provider routes (claim, result, permit), expecting `command_not_found` in the bridge body; (b) the facade routes `GET /orders/{order_id}` and the #985 `read_command_result`, `read_approval`, dispatch and cancel, expecting `not_found` in the #957 §4 body; (c) the #986 read extension, asserted in process on its four sentinels (not found, expired, binding mismatch, not authorized) and their #957 §4.2 mapping (`unavailable` without an M1a state, a connection code with one). Byte identity is asserted between the absent and the foreign case inside one surface only. Each case first asserts that the foreign row exists.
10. **Audit and metrics.** A capture `audit` sink and a fresh `prometheus.Registry` record every path. The effect id appears only redacted (prefix plus hash), the principal and tenant are present, the actor is the control worker's `glovo.Actor` (#959 `WithActor`/`ActorFrom`, delegated by name to #959 T23), the intent appears only as its hash, the receipt id and outcome are present, and no `lt_` token, raw effect id or foreign tenant string appears in any record or label value.
11. **Contract pins (F6).** `testdata/PINS` lists, per owner, the digest of the checked-in file set: #1059 `SHA256SUMS` (as vendored by #986, and the basket subset by #988), #985 `internal/glovo/control/contract/SHA256SUMS` and the #957 `internal/glovojoin/contract/` digest. `TestGlovoContractPinsMatch` recomputes them and fails on any difference. Every message of the end-to-end run is validated against the owner's schema (control request and 200 bodies, the v1alpha2 command and read result, the facade bodies). `testdata/p1/` holds the transcript of the run, one JSON document per hop, with a `PROVENANCE` that says "evidence, not a contract; the owners' files in PINS are authoritative". Peers do not vendor it, and this slice opens no PR in a peer repository.
12. **Negative matrix and delegation (F7).** The table of requirements.md is the list. `docs/glovo-p1-contract.md` records, for every delegated row, the Go test function name that the owner's task produced (task 0). The CI step takes the list of own and delegated names from a checked-in `testdata/required-tests.txt` and fails on a missing name, a `--- SKIP` or no `--- PASS` line, so a renamed, skipped or deleted sibling test turns it red. Each own test has the mutation of requirements.md recorded in the doc, with the red result.
13. **CI evidence step.** A new step in `validate.yml`, "glovo P1 contract tests (fail-closed evidence)", copies the existing bridge step: `go test -p 1 -count=1 -v -tags glovojoin_fixture -run 'TestPGGlovoContract|TestGlovoContract' ./internal/glovo/contract/ ./internal/glovo/contract/fakeprovider/`, plus the delegated packages, fails on `--- SKIP` and requires the named PASS list. It also runs the release-build check that no gate-opening symbol is present. The log is uploaded as an artifact so it can be attached to the P1 acceptance.
14. **Docs.** `docs/glovo-p1-contract.md` gives the evidence map (acceptance criterion to test name), the symbol and test-name register, the mutation table and how to re-run locally.

Why this approach: PG row and advisory locks give deterministic race ordering that time-based tests cannot. The stores' real transactions under the real role split are what implement exactly-once, so mocks, a superuser connection or a self-enqueued command would prove nothing about the path production runs. The fail-closed CI step pattern already guards against silently skipped evidence.

## Alternatives

- **Live e2e against a preview deployment (`e2e/`, build tag `e2e`).** Rejected: the bridge and the glovo gate are dark by policy (`docs/bridge.md` deployment gates), so enabling them for tests would breach the gates. It is also non-deterministic for races.
- **A separate cross-repo harness repo that runs mctl-api, mctl-agents and mctl-telegram together in docker-compose.** Rejected for P1. It is a heavy new CI surface with cross-repo credentials, and it races by timing. Pinned owner files give the same contract guarantee with each repo staying authoritative for its own side. It could be revisited for P2.
- **Own golden fixtures that peers vendor (the earlier draft).** Rejected (F6): it creates a second authoritative copy of files that #985, #1059 and #957 already own.
- **Mock-based unit tests with a fake `WriteFence`, or a direct `Store.Enqueue`.** Rejected: `allowFence` proves nothing about `aar_` revocation, tenant membership or intent hash binding, and a self-enqueued command is not the one #985 reserved the `aar_` for. The acceptance criteria need the real fence from #989 and the real dispatch from #985.

## Platform impact

- No production migration, no production runtime change, no new production env var, no route, no MCP tool (the `server_test.go` tool count is unchanged). `glovo.Default` and `glovo.ControlDefault` stay closed. The harness applies the siblings' schemas, but only to a throwaway database that the test creates and drops.
- CI runtime grows by an estimated 2-3 minutes on the existing `postgres:16` service, because the harness builds a database and applies the chain. The package keeps the `-p 1` serial convention. The server needs a role with `CREATEDB` and `CREATEROLE`; the CI superuser has both.
- Risk: flaky race tests. Mitigation: ordering is by observed `pg_locks` waits with a bounded context that fails rather than hangs, a non-vacuity precondition in each test, and a `-count=20` stability run before merge.
- Risk: the dependency slices change their APIs or tests before merge. Mitigation: implementation starts only after the full set of the merge order in requirements.md has merged; the symbol and test-name register is checked by CI.
- Risk: contract drift. Mitigation: the digests in `testdata/PINS` and the schema validation of every run message fail this slice's CI when any owner's file set changes, and the owner's PR must bump the pin in the same wave.

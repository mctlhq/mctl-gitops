# Design: issue-990-feat-glovo-m1b-4-cross-repo-contract-tes

## Current state
- `internal/bridge/` implements the command bridge (mctl-api#962, documented in `docs/bridge.md`). It is a Postgres command outbox, a claim endpoint with leases (`lease_epoch`, a rotating private `lease_nonce`), an exactly-once result CAS, and `IssueWritePermit` in `internal/bridge/permit.go`. The bridge is dark: `MCTL_BRIDGE_ENABLED` gates it in `cmd/api/main.go` (around lines 1013-1024).
- `WriteFence` (`internal/bridge/permit.go`) is the transaction-compatible hook to the #954 fence. `Check(ctx, tx, FenceBinding)` is meant to lock the `aar_` approval row and verify tenant, owner, connection, install revision, `IntentHash` and the unexpired/unrevoked state. The only implementation in the clone is `refusingFence`, which always returns `ErrWriteFenceUnavailable`. Tests use `allowFence` (`internal/bridge/store_pg_test.go:33`).
- Effect states are `none`, `permitted`, `succeeded`, `failed`, `not_performed` and `unknown`, defined in `internal/bridge/store.go` (around line 50 and the CHECK at line 108). A reclaim or an expiry turns `permitted` into `unknown` (store.go around lines 637, 830 and 877). That is the existing mechanism the "ambiguous effect gives unknown" requirement depends on.
- Existing PG evidence includes `TestPGReclaimAfterPermitMarksEffectUnknown`, `TestPGWritePermit` and `TestPGClaimResultReplayAndTenancy` in `store_pg_test.go`, and `TestPGExpiredLeasedPermitIsUnknownAndAudited` in `hardening_test.go`. Each covers one store transition. None of them chains the full P1 flow, uses a real fence, or forces a race order.
- Wire schemas are vendored from mctl-agents#1045 in `internal/bridge/schema/` with `PROVENANCE` (sha256 per file) and `TestVendoredSchemasMatchProvenance` (`schema_test.go:24`). Fixtures live in `internal/bridge/schema/testdata/` (`command.valid.json`, `result.valid.json` and negatives). This is the pinning pattern this slice reuses.
- `internal/glovo/` has only the closed `Gate` (`gate.go`, `glovo.Default{Open:false}`) and the typed errors (`errors.go`). `docs/glovo-auth.md` documents the audience plumbing (M1a slice 1). `internal/api/glovo_audience_gate.go` refuses Glovo-audience tokens on every route.
- `aar_` approval binding is implemented in `internal/api/approval_binding.go` (`MCTL_APPROVAL_BINDING` off/observe/enforce) and `handlers_approval_grant.go`.
- CI (`.github/workflows/validate.yml`) runs `go test -p 1 ./...` against a `postgres:16` service. It also has a separate "bridge PostgreSQL tests (fail-closed evidence)" step, which runs `-run 'TestPG' ./internal/bridge/`, fails on any `--- SKIP` and requires named `--- PASS` lines. PG tests skip locally without `TEST_DATABASE_URL`.
- `e2e/e2e_test.go` sits behind `//go:build e2e` and targets a live deployment. It is unsuitable here because the bridge is dark in every deployment.
- The clone does not contain #988 (M1b/1), #989 (M1b/2), #985 (M1b/3) or #986 (read extension). `git log` ends at `ceac9ed` (#984).

Deployed state checked:
- `mctl_get_service_config(team=admins, service=mctl-api)` returned "service not found: admins/mctl-api". The tenant/service binding of mctl-api was not observed.
- `$MCTL_GITOPS_ROOT` `services/` holds tenants `admins`, `karabu`, `labs` and `namax66`. `services/admins/` lists no `mctl-api` directory, so the deployed values (including whether `MCTL_BRIDGE_ENABLED` is set) were not observed. This change is test-only and needs no deployed flag, but the gap is recorded under Open questions.

## Proposed solution
Add a test-only package, `internal/glovo/contract`, with a PG-backed suite. It adds no new production code paths except a tiny loopback-only fake provider and test helpers, which live in `_test.go` files or in `internal/glovo/contract/fakeprovider` with no `cmd/` import.

1. **Golden fixtures with sha256 pins.** `internal/glovo/contract/testdata/p1/` holds one JSON document per hop: history request/response, preview, basket, prepare (with intent hash), `aar_` approval decision, bridge command (v1alpha1 mutation), fake-provider effect record, bridge result and order status. Each document is validated against `internal/bridge/schema/*.schema.json` where applicable. A `PROVENANCE` file lists the sha256 of every fixture plus the peer references (mctl-agents#1044, mctl-telegram#1262 and #1264). `TestGlovoContractFixturesMatchProvenance` mirrors `TestVendoredSchemasMatchProvenance`. The peers vendor the directory byte for byte and run their own provenance test. Any drift on either side breaks CI on both sides.
2. **Fake provider.** This is an in-process `httptest` server bound to 127.0.0.1. It acts as the provider worker: it claims (`Store.Claim` or the HTTP route via the bridge router), asks for the write permit, performs a synthetic "order" in memory keyed by `command_id` (idempotent, with read-back), and posts the result. It exposes `Writes(commandID) int` and fault knobs: `AmbiguousEffect`, `DropResultPost`, `CrashAfterPermit` (discard in-memory state and stop) and `DuplicateResultPost`. A guard `net.Dialer` check fails the test if any non-loopback address is dialed.
3. **Flow test.** `TestPGGlovoContractHappyPath` drives history -> preview -> basket -> prepare through the M1b/1-3 APIs. It then creates the `aar_` approval through the approval-grant path, enqueues the command, and lets the fake provider dispatch. It asserts one write, `effect_state=succeeded` and the order status, and checks every hop's payload against the golden fixture. Volatile fields (ids, timestamps) are normalized by a single documented normalizer before comparison.
4. **Deterministic race (`revoke-after-approval-before-write`).** Two explicit transactions are used and ordered by the database's row lock, not by sleeps.
   - *Revoke wins:* tx A runs the revoke and holds the `aar_` row with `SELECT ... FOR UPDATE`. `IssueWritePermit` starts in a goroutine and blocks inside `WriteFence.Check` on the same row (confirmed through `pg_stat_activity.wait_event_type='Lock'` polling, not a timer). A commits, the permit gets `write_fence_refused`, and the test asserts 0 fake writes, `effect_state=none`, no permit row and an audited refusal.
   - *Write wins:* the permit tx holds the row and a revoke blocks on it (confirmed the same way). The permit commits, the fake provider writes once, then the revoke commits. Any retry (a second permit, a reclaim followed by a permit, or a duplicate result) is denied, and the test asserts exactly 1 write and 1 audit record.
5. **Ambiguity and recovery matrix** (`TestPGGlovoContractUnknown*`): an ambiguous provider reply; a crash after the permit followed by lease expiry and reclaim under `lease_epoch+1`; a lost result post followed by the `Expirer` sweep; and a stale-token result from the old holder (`lease_stale`). Each case asserts `effect_state=unknown`, no second permit (`permit_already_issued`) and `Writes==1` (or 0 when the crash comes before the effect).
6. **Exactly-once under retries** (`TestPGGlovoContractExactlyOnce`): N concurrent claimers, duplicate result posts (replay gives `replayed:true`, a different digest gives `result_conflict`) and a re-enqueue of the same operation key. Asserts one effect per approved intent.
7. **Isolation matrix** (`TestPGGlovoContractIsolation`): a table over {tenant A, tenant B} x {principal 1, principal 2} x {claim, result, permit, order status, receipt read, #986 read extension}. Every foreign access answers not-found with an identical body shape. The #986 cases also cover expired, revoked and wrong-digest refusals.
8. **Audit and metrics assertions.** A capture `audit` sink and a fresh `prometheus.Registry` record every path. Assertions: the effect id appears only redacted (prefix plus hash), the principal and tenant are present, the intent appears only as its hash, the receipt id and outcome are present, and no `lt_` token, raw effect id or foreign tenant string appears in any record or label value.
9. **CI evidence step.** A new step in `validate.yml`, "glovo P1 contract tests (fail-closed evidence)", copies the existing bridge step: `go test -p 1 -count=1 -v -run 'TestPGGlovoContract|TestGlovoContract' ./internal/glovo/contract/`. It fails on `--- SKIP` and requires a named PASS list. The log is uploaded as an artifact so it can be attached to the P1 acceptance.
10. **Docs.** `docs/glovo-p1-contract.md` gives the evidence map (each acceptance criterion to its test name), the fixture-pinning procedure for peers, and how to re-run locally.

Why this approach: PG row locks give deterministic race ordering, which time-based tests cannot. The stores' real transactions are what implement exactly-once, so mocks would prove nothing. The existing fail-closed CI step pattern already guards against silently skipped evidence.

## Alternatives
- **Live e2e against a preview deployment (`e2e/`, build tag `e2e`).** Rejected: the bridge and the glovo gate are dark by policy (`docs/bridge.md` deployment gates), so enabling them for tests would breach the gates. It is also non-deterministic for races.
- **A separate cross-repo harness repo that runs mctl-api, mctl-agents and mctl-telegram together in docker-compose.** Rejected for P1. It is a heavy new CI surface with cross-repo credentials, and it races by timing. Pinned fixtures give the same contract guarantee with each repo staying authoritative for its own side. It could be revisited for P2.
- **Mock-based unit tests with a fake `WriteFence`.** Rejected: `allowFence` already exists and proves nothing about `aar_` revocation, tenant membership or intent hash binding. The acceptance criteria need the real fence from #988/#989.

## Platform impact
- No migrations, no runtime change, no new env var, no route, no MCP tool (so the `server_test.go` tool count is unchanged). `glovo.Default` stays closed.
- CI runtime grows by an estimated 1-2 minutes on the existing `postgres:16` service. Tests share `TEST_DATABASE_URL`, so they must keep the `-p 1` serial convention and clean up only rows they created (filtered by a per-test tenant prefix) to avoid wiping other packages' rows.
- Risk: flaky race tests. Mitigation: ordering is by observed lock waits (`pg_stat_activity`), with a bounded context timeout that fails rather than hangs, and the suite is run `-count=20` once before merge.
- Risk: the dependency slices change their APIs before merge. Mitigation: implementation starts only after #985, #986, #988, #989 and mctl-telegram#1262 are merged. Fixture regeneration is a single documented command.
- Risk: fixture drift between repos. Mitigation: sha256 PROVENANCE on every side, and changes are coordinated in one PR set, as already done for the v1alpha1 schemas.

## Rollback

- Every switch is an env var: revert in reverse order (`OAUTH_JWT_ACCEPT_HS256=true`, then `OAUTH_JWT_SIGNING_ALG=HS256`, then `OAUTH_JWT_REQUIRE_AUD=false`). Because HS256 acceptance is turned off last and back on first, reverting the signing algorithm never strands tokens: EdDSA tokens already issued keep validating as long as their key remains in `OAUTH_JWT_SIGNING_KEYS` (keep it as retained for one retention window).
- Full code rollback: redeploy the previous image. Tokens minted by this build with `aud` remain valid HS256 tokens for the old build (it ignores `aud`); EdDSA tokens would be refused by the old build, so roll back `OAUTH_JWT_SIGNING_ALG` to HS256 first and wait one TTL, or accept a forced re-login (refresh tokens are unaffected and re-mint HS256 access tokens).
- Do not roll back past step A once any service mints tokens with a non-API audience (ordering constraint); the old build would accept them.

## Tests

All tests are in `internal/mcp/support_test.go` unless noted. mctl-support is faked with `httptest.Server`, and each test records the requests the fake receives.

- [ ] T1. Tenant refusal in mctl-api: a user without the tenant in their groups calls `mctl_ask_support`. The result is a tool error with `tenant_forbidden`, and the fake receives zero requests. The test must fail if the `supportTenantAllowed` check is removed.
- [ ] T2. Refusal by mctl-support is surfaced: the caller passes the mctl-api check, and the fake answers 403 with an A2A error body. The result is a tool error naming 403, not an empty answer. The second "Done when" test, that mctl-support itself refuses, lives in mctlhq/mctl-support and is referenced in the PR.
- [ ] T3. Stdio path: there is no user in the context. A whoami stub returning groups without the tenant leads to a refusal. A whoami stub returning 500 leads to a refusal. In both cases the fake receives zero requests.
- [ ] T4. Request shape: the fake asserts `POST /message:send`, `A2A-Version: 1.0`, `Authorization` equal to the caller's own token byte for byte, `metadata.tenant`, the text part equal to the question, and `contextId` present only when `context_id` is given.
- [ ] T5. Parity: the recorded fixture from task 1 is served by the fake (send reply, one WORKING poll, then COMPLETED). The MCP tool result equals `renderSupportAnswer` applied to the directly decoded fixture task (deep equality on the decoded JSON).
- [ ] T6. Timeout: the fake stays WORKING and the wait is 50ms. The result is non-error, with the task id, `terminal:false` and the `mctl_get_support_task` note. A follow-up `mctl_get_support_task` against a COMPLETED fixture returns the answer.
- [ ] T7. Terminal failures: FAILED, REJECTED and CANCELED (in both `TASK_STATE_` and short forms) each return a tool error containing the state and the status message reason.
- [ ] T8. Failure is not absence: a connection refused error, a 500, a 302 redirect (the redirect target receives no request), a non-JSON body and a JSON body that is neither a task nor a message each produce a tool error.
- [ ] T9. Interrupted states: INPUT_REQUIRED returns a non-error result immediately with the state, reason and context id, and no further polls are made.
- [ ] T10. Argument validation: an empty or oversized question, a tenant containing `/`, an `id` of `..` or `a/b`, and a non-string `context_id` are all refused with no upstream request.
- [ ] T11. Not configured: with no `SetSupportConfig`, both tools return the "not configured" tool error.
- [ ] T12. Agent scope: a `support`-scoped run token calling `mctl_ask_support` is refused with `agent_scope_denied` (extend `internal/mcp/agent_scope_test.go`).
- [ ] T13. Write deadline (`internal/api`): with `MCPWriteTimeout` set, a `/mcp` handler that sleeps longer than `ServerWriteTimeout` but shorter than `MCPWriteTimeout` still writes its response, using a test `http.Server` with a short WriteTimeout and scaled durations.
- [ ] T14. Config parsing: invalid `SUPPORT_A2A_URL` values (relative, `http://` to a non-loopback host) and `SUPPORT_ASK_WAIT` values above 90s fail startup validation.

## Rollback

- Fast path, no deploy of code: remove `SUPPORT_A2A_URL` from `bootstrap/templates/mctl-platform/mctl-api.yaml` in mctl-gitops. Both tools then answer "not configured", and the `/mcp` write deadline returns to 30s. Optionally, set both tools to `enabled: false` in `docs/portal-allowlist.json` to hide them on the portal.
- Full rollback: revert the mctl-api PR. That removes the tools, the hint and allowlist entries, and the receipt gate set change (the policy version returns to v1). No data migration is involved, and mctl-support is unaffected.

## Tests

All tests are in `internal/mcp/support_test.go` unless noted. mctl-support is faked with `httptest.Server` serving the task 1 fixtures, and each test records the requests the fake receives. Every fixture-based test asserts literal expected values written in the test, not only equality with `renderSupportAnswer`.

- [ ] T1. Tenant refusal in mctl-api: a user without the tenant in their groups calls `mctl_ask_support`. The result is a tool error with `tenant_forbidden`, and the fake receives zero requests. The test must fail if the `supportTenantAllowed` check is removed.
- [ ] T2. Refusal by mctl-support is surfaced: the caller passes the mctl-api check, and the fake answers 403 with an A2A error body. The result is a tool error naming 403, not an empty answer and not `support_send_outcome_unknown`. The second "Done when" test, that mctl-support itself refuses, lives in mctlhq/mctl-support and is referenced in the PR.
- [ ] T3. Stdio path: there is no user in the context. A whoami stub returning groups without the tenant leads to a refusal. A whoami stub returning 500 leads to a refusal. In both cases the fake receives zero requests.
- [ ] T4. Request shape: the fake asserts `POST /message:send`, `A2A-Version: 1.0`, `Authorization` equal to the caller's own token byte for byte, request-level `metadata.tenant` (and no `message.metadata.tenant`), `configuration.returnImmediately == true`, **no `blocking` key anywhere in the body**, `role == "ROLE_USER"`, the text part equal to the question, a non-empty `messageId`, and `contextId` present only when `context_id` is given.
- [ ] T5. MCP vs direct REST parity on the main contract fixture: the fake serves `send_task_submitted.json`, one `task_working.json` poll, then `task_completed_status_message.json`. Separately, the test performs its own plain `GET /tasks/{id}` against the same fake with the same bearer and decodes the body without the tool. The MCP tool result must deep-equal `renderSupportAnswer` of that directly fetched task, **and** must equal the literal expected answer: `answer_source == "status_message"`, `text` equal to the fixture's text part, `result` byte-equal to the fixture's data part (all six `SupportResult` keys present), no `additional_data`.
- [ ] T6. Timeout: the fake stays WORKING and the wait is 50ms. The result is non-error, with the task id, `terminal:false` and the `mctl_get_support_task` note. A follow-up `mctl_get_support_task` against `task_completed_status_message.json` returns the same literal answer as T5.
- [ ] T7. Terminal failures: `task_failed.json`, `task_rejected.json` and `task_canceled.json` (plus short-form state variants) each return a tool error containing the state and the reason text from `status.message`.
- [ ] T8. Failure is not absence: on a poll, a 500, a 302 redirect (the redirect target receives no request), a non-JSON body and a JSON body that is neither a task nor a message each produce a tool error naming the task id once the budget ends; a connection refused on the send produces `support_send_outcome_unknown`.
- [ ] T9. Interrupted states: `task_input_required.json` returns a non-error result immediately with the state, reason and context id, and no further polls are made.
- [ ] T10. Argument validation: an empty or oversized question, a tenant containing `/`, an `id` of `..` or `a/b`, and a non-string `context_id` are all refused with no upstream request.
- [ ] T11. Not configured: with no `SetSupportConfig`, both tools return the "not configured" tool error.
- [ ] T12. Agent scope: a `support`-scoped run token calling `mctl_ask_support` is refused with `agent_scope_denied` (extend `internal/mcp/agent_scope_test.go`).
- [ ] T13. Write deadline (`internal/api`): with `MCPWriteTimeout` set, a `/mcp` handler that sleeps longer than `ServerWriteTimeout` but shorter than `MCPWriteTimeout` still writes its response, using a test `http.Server` with a short WriteTimeout and scaled durations.

### Send semantics and the wait budget (amendment 2026-10-27)

- [ ] T21. Non-blocking send: the fake returns `send_task_submitted.json` at once and COMPLETED on the second poll. The tool returns the T5 answer, the fake saw exactly one `POST /message:send`, and polls were spaced by `PollInterval` (fake clock or tolerant bounds).
- [ ] T22. Shared deadline: with `Wait = 300ms`, the fake delays the send reply by 200ms and then stays WORKING. The tool returns `terminal:false` within `300ms + small margin` (not `200ms + 300ms`), proving polling did not get a fresh budget. A second case: the send reply takes longer than the whole budget, and the tool returns `support_send_outcome_unknown` at the budget, not later.
- [ ] T23. Blocking-server compatibility: the fake ignores `returnImmediately`, holds the send for less than the budget, then replies with a COMPLETED task. The tool renders it without any `GET /tasks/{id}`.
- [ ] T24. Outcome unknown, no resend: for each of send transport error, send 502, send budget expiry, and an undecodable 2xx send body, the tool returns `support_send_outcome_unknown` naming the `messageId` it sent, the fake saw exactly one `POST /message:send`, and zero `GET /tasks/...` requests.
- [ ] T25. Poll errors with a known id: one poll answers 503 and the next COMPLETED, and the tool returns the answer (retry within budget). A poll answering 404 stops at once with a tool error naming the task id, with no further polls.
- [ ] T26. `mctl_get_support_task` timeout: the fake holds `GET /tasks/{id}` longer than `RequestTimeout`, and the tool returns a tool error naming the task id within `RequestTimeout + margin`.

## Rollback

- Fast path, no deploy of code: remove `SUPPORT_A2A_URL` from `bootstrap/templates/mctl-platform/mctl-api.yaml` in mctl-gitops. Both tools then answer "not configured", and the `/mcp` write deadline returns to 30s. Optionally, set both tools to `enabled: false` in `docs/portal-allowlist.json` to hide them on the portal.
- Full rollback: revert the mctl-api PR. That removes the tools, the hint and allowlist entries, and the receipt gate set change (the policy version returns to v1). No data migration is involved, and mctl-support is unaffected.

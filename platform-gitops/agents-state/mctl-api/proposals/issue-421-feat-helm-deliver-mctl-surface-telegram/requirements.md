# Deliver MCTL_SURFACE_TELEGRAM_TOKEN from an optional surfaceTelegramTokenSecret

## Context

`mctl-api` authenticates the `surface:telegram` principal from the
`MCTL_SURFACE_TELEGRAM_TOKEN` environment variable. `internal/auth/oidc.go`
maps it in `surfaceTokenEnv` (`"telegram": "MCTL_SURFACE_TELEGRAM_TOKEN"`),
`surfaceTokens()` reads it at middleware construction time, refuses it if it
is shorter than `minSurfaceTokenLen` (32), equal to `MCTL_AGENT_SERVICE_TOKEN`,
or shared with another surface, and otherwise mints `NewSurfaceUser("telegram")`
for callers presenting it. Nothing in this repository's Helm chart can deliver
that variable: `helm/values.yaml` and `helm/templates/deployment.yaml` know
about `usageWriterTokenSecret`, `githubAppTokenSecret`, `envFromSecret` and
`postgresCA`, but there is no `surfaceTelegramTokenSecret`.

mctl-gitops has already done its half. `platform-gitops/bootstrap/templates/
mctl-platform/mctl-api-surface-telegram.yaml` renders an ExternalSecret named
`mctl-api-surface-telegram` whose only `data` entry is `secretKey:
MCTL_SURFACE_TELEGRAM_TOKEN` (from Vault `platform/mctl-api/surface-tokens`,
property `telegram-token`), and `mctl-api.yaml:245` passes
`surfaceTelegramTokenSecret: mctl-api-surface-telegram` into the chart — both
behind the `surfaceTelegramToken.enabled` flag, which `bootstrap/values.yaml`
still holds at `false` and annotates as "owner step 0 has not landed". Because
Helm silently ignores unknown values, that reference is inert today: even after
the Vault write and the flag flip, the pod would never see the variable and
every relay call from `labs-mctl-telegram` would get 401. This proposal lands
owner step 0 — the last code prerequisite for the live proof of
mctlhq/mctl-telegram#443.

## User stories

- AS the platform owner I WANT the mctl-api chart to accept an optional
  `surfaceTelegramTokenSecret` SO THAT flipping `surfaceTelegramToken.enabled`
  in mctl-gitops actually delivers `MCTL_SURFACE_TELEGRAM_TOKEN` to the pod and
  the `surface:telegram` principal authenticates.
- AS an mctl-api maintainer I WANT the new value to default to empty and render
  byte-identical output SO THAT shipping the chart ahead of the gitops flag
  changes nothing in production.
- AS an mctl-api maintainer I WANT `helm/render_test.go` to assert the env entry,
  the Secret name and the Secret key SO THAT the block cannot be deleted or the
  key silently drifted from what the ExternalSecret produces.
- AS an SRE I WANT a Secret that has not synced yet to leave the principal
  disabled rather than block the pod SO THAT a Vault or ESO delay never takes
  the control plane down.

## Acceptance criteria (EARS)

- WHEN `surfaceTelegramTokenSecret` is set to a non-empty string THE SYSTEM
  SHALL render, in the `mctl-api` container's `env` list, exactly one entry
  named `MCTL_SURFACE_TELEGRAM_TOKEN` whose `valueFrom.secretKeyRef.name`
  equals that value, whose `key` is `MCTL_SURFACE_TELEGRAM_TOKEN`, and whose
  `optional` is `true`.
- WHEN `surfaceTelegramTokenSecret` is unset (chart default `""`) THE SYSTEM
  SHALL render no `MCTL_SURFACE_TELEGRAM_TOKEN` env entry.
- WHEN `surfaceTelegramTokenSecret` is explicitly set to the empty string THE
  SYSTEM SHALL render output byte-identical to the default render.
- WHILE `surfaceTelegramToken.enabled` is `false` in mctl-gitops
  `bootstrap/values.yaml` THE SYSTEM SHALL render the production mctl-api
  manifest unchanged from today.
- IF the referenced Secret does not exist or lacks the key THEN THE SYSTEM
  SHALL start the pod normally with the `surface:telegram` principal disabled,
  because the `secretKeyRef` is `optional: true` — mirroring
  `usageWriterTokenSecret` (`helm/templates/deployment.yaml:56-66`).
- WHEN the chart is rendered with and without `surfaceTelegramTokenSecret` THE
  SYSTEM SHALL pass `helm lint .` in both configurations.
- IF the `secretKeyRef` block is removed from `helm/templates/deployment.yaml`
  THEN the set-case test in `helm/render_test.go` SHALL fail.
- WHEN `surfaceTelegramTokenSecret` and `usageWriterTokenSecret` are both set
  THE SYSTEM SHALL render both env entries independently, neither suppressing
  the other.

## Out of scope

- Any Vault write, token generation, or flag change in mctl-gitops (owner gates
  those on mctlhq/mctl-telegram#443). This proposal changes only the mctl-api
  repository.
- Any change to `internal/auth` — `surfaceTokenEnv`, `surfaceTokens()`,
  `minSurfaceTokenLen` and the middleware wiring stay exactly as they are.
- `MCTL_SURFACE_PORTAL_TOKEN`, the other entry in `surfaceTokenEnv`. It has no
  gitops ExternalSecret yet; adding a chart value for it would be speculative.
- Any change to `helm/templates/deployment.yaml` volumes, volumeMounts, probes
  or resources.
- CHANGELOG.md, which is generated by the release tooling.

## Open questions

- The issue says "plus the key-name value if the usage-writer pattern has one".
  It does not: `helm/templates/deployment.yaml:64` hardcodes
  `key: MCTL_USAGE_WRITER_TOKEN` and `helm/values.yaml:111` exposes only
  `usageWriterTokenSecret`. Mirroring "exactly" therefore means **no**
  `surfaceTelegramTokenKey` value; the key is hardcoded to
  `MCTL_SURFACE_TELEGRAM_TOKEN`, which is what
  `mctl-api-surface-telegram.yaml`'s `secretKey` produces. Proceeding on that
  reading; a key override can be added later if a second Secret layout appears.
- `helm/render_test.go`'s `envVar` struct currently has only `name` and `value`
  fields, so a `valueFrom` env unmarshals with an empty `Value` and cannot be
  asserted on. The test file needs a small `valueFrom`/`secretKeyRef` struct
  addition. Treated as in-scope test plumbing, not a separate change.
- Whether the existing `usageWriterTokenSecret` block deserves the same
  render-test coverage while the plumbing is being added. Recommended as a
  cheap bonus assertion but not required by the issue; captured as an optional
  task.

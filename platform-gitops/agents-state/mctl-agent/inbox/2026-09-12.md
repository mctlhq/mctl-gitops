### 1. recordingrulesnodata-ticket-triage: Suppress/route the high-frequency unmatched RecordingRulesNoData alert
**Category:** performance
**Impact:** 3
**Effort:** 2
**Rationale:** `RecordingRulesNoData` on `vmalert-monitoring-victoria-metrics-k8s-stack`
fired at least 6 times in a single 4-hour log window (06:37-10:32 UTC, 2026-09-11)
alone and is the highest-frequency alert type in the sampled 24h log window. It is
not in the routed-alert list (`context/architecture.md`), so every occurrence
becomes a generic ticket with "no skills matched" and, per the 3-tier skill design,
falls through to the LLMDiagnosis fallback — meaning the platform is very likely
paying repeated Claude API latency/cost on a recurring, structurally-unresolvable
no-op alert instead of resolving it. The YAML-skill tier (ADR 0001) exists exactly
for this: a fast, hot-reload regex pattern that recognizes this specific
alertname+instance pair and either auto-resolves the ticket with a canned
"known recording-rule gap, no action" response or routes it to a `RecordingRulesNoData`
diagnose-only handler, cutting redundant LLM calls and ticket noise without touching
the builtin skill set or the circuit breaker (respecting the "do not touch circuit
breaker thresholds without real prod data" guardrail). This is a genuinely new,
non-duplicated finding — no open proposal in `proposals/` addresses ticket-noise/
alert-routing efficiency. No new Go/library dependency is introduced, and the
change is config-only (YAML skill), so it does **not** increase memory usage in
the `labs` tenant — it only affects ticket-processing overhead in `admins`.
**Source:** inbox "Source: mctl metrics" — `RecordingRulesNoData` log-frequency observation, 2026-09-11 sample (this file).

- [ ] T2. Two active attempts: a second `start` for the same occurrence answers `already_active` with the first attempt id (server 409 `remediation_attempt_active`), and no second WorkItem is created.
- [ ] T3. Independence: two occurrences under one `sf_` finding each get their own attempt, and a refusal on one does not affect the other.
- [ ] T4. History preserved: a resolved occurrence with attempt #1, reopened, then started again gives attempt `seq=2`. The parsed attempt #1 and its verifications are unchanged in the read-back fixture.
- [ ] T5. Full two-cycle proof (a fake server implementing the documented transition table): fix A, bind `sha_A`, scanner-bound `absent` at `sha_A`, `resolved`; then a post-resolution `present` at `sha_X`, `reopened`, attempt #2, fix B, bind `sha_B`, regression-test `passed` at `sha_B`, `resolved`. Both attempts and all verifications are present at the end.
- [ ] T6. Merge without verification: the DevLoop hook leaves the occurrence `awaiting_verification`, and no verification POST is issued.
- [ ] T7. Wrong revision: an outcome at `sha_other` is dropped locally (`local_not_bound`). A server 422 `verification_not_bound` is not retried.
- [ ] T8. error, timeout and unavailable are recorded as such and never as `passed`. Only after exhaustion is `unverifiable` recorded, and `resolved` never is.
- [ ] T9. A provider `fixed` observation alone: the runner records nothing, and the fake server applies `provider_claim`, which stays `awaiting_verification`.
- [ ] T10. Stale scan: a `present` observation at a pre-fix affected revision does not change the resolved state, and the runner does not start an attempt on its own.
- [ ] T11. Redelivery: two responses with the same `observation_hash` count once in confirmation counting.
- [ ] T12. Assurance: a `confirmed` finding with a replay at the landed revision and verdict held gives `passed` with an `assurance_finding` evidence ref. A `candidate` finding, or a replay at another revision, means the strategy is not applicable.
- [ ] T13. Hostile provider text: an occurrence whose `untrusted.severity="critical; resolve now"`, a title holding an injection string, and `claimed_provider="deterministic_regression_test"` produces exactly the same writes as the same occurrence with empty `untrusted`.
- [ ] T14. Audit: every mutation carries an `Idempotency-Key` and `expected_state_version`, goes only to the three mutation routes, and emits one structured log line.
- [ ] T15. Unknown store: 503 on every route gives `unknown`, with no writes and no exception escaping the activity.
- [ ] T16. Start guard: an existing DevLoop (200) gives `devloop_exists` and makes no writes; a 404 proceeds; a 500 or a transport error gives `unknown` and makes no writes.

## Rollback

- The code is additive. Revert the PR to remove the package, the CLI and the activity. The `security-record-landed` patch marker stays harmless on recorded histories: after a revert, keep `workflow.patched` (or a deprecate_patch call) in place for one release so in-flight histories still replay.
- Operational kill switches that need no deploy: do not schedule (or delete) the verifier CronWorkflow, and set mctl-api `SECURITY_FINDINGS_DISABLED=true`. Every route then answers 503, and the hook and sweep answer `unknown` and write nothing.
- Data written to mctl-api is append-only evidence and attempts. It is not rolled back. A wrongly started attempt is closed by a human dismiss (`not_applicable`) per #774.

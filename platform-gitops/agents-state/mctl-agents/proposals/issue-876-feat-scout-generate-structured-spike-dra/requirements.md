# Scout: generate structured, decision-grade spike drafts

## Context
The daily scout (`orchestrator/run_scout.py`) sends a Telegram digest. Each item has a "Draft spike N" URL button that opens a prefilled GitHub issue form, and a "Create spike N" callback button that mctl-agent (`internal/scoutspike`) handles by reading the draft back from that URL. `orchestrator/scout/render.py:draft_body()` currently renders only six header lines (`Source`, `Question`, `Outcomes`, `Lifecycle`, `Related`, `Why mctl`) and a `Generated by` footer. The owner then adds the same research structure to every spike by hand: duplicate/current-state check, bounded experiment, measurements, invariants, deliverables and non-goals.

The issue asks for every scout-generated spike to start as a small, decision-grade research contract. The existing machine-sensitive contracts must not change: `Source:` stays the first line (the dedupe regex `_SOURCE_RE` in `orchestrator/scout/dedupe.py` keys on it), the `MAX_BUTTON_URL_CHARS = 2000` fallback stays, and the button texts and `scout:create:N` callback stay. The scaffold also has to be compact. The button URL carries the body, and the URL fallback reduces the body to `Source:` only, so a verbose scaffold would turn most drafts into `Source:`-only issues when "Create spike" is used.

## User stories
- AS the spike owner I WANT scout-created spikes to already contain duplicate-check, experiment, measurement, invariant, deliverable and non-goal sections SO THAT I do not rewrite every issue before investigation.
- AS the issue-investigator I WANT a spike body that starts with duplicate/current-state verification and a bounded experiment SO THAT I can begin research without first restructuring the issue.
- AS the operator of mctl-agent's scout callback I WANT the button texts, callback data and URL fallback unchanged SO THAT "Create spike N" keeps working.

## Acceptance criteria (EARS)
- WHEN `draft_body(item, run_id)` is called THE SYSTEM SHALL return a body that contains, in order, the six header lines `Source:`, `Question:`, `Outcomes:`, `Lifecycle: proposed`, `Related:`, `Why mctl:`, then the sections `## Existing / duplicate check`, `## Required experiment`, `## Measurements`, `## Invariants`, `## Deliverables`, `## Non-goals`, then the line `Generated by mctl-agents scout, run <run_id>.`
- WHEN a draft body is rendered THE SYSTEM SHALL make `Source: <link>` the first line, so that `_SOURCE_RE` in `orchestrator/scout/dedupe.py` still extracts the link.
- WHEN a draft body is rendered THE SYSTEM SHALL state in the scaffold that `Related` candidates must be verified against current issues and code, and that `unknown` is distinct from zero or success.
- WHILE an item's `question`, `outcomes` and `why_en` are at their schema maxima (240, 60 and 200 characters, from `orchestrator/scout/scoring.py`), `related` holds 3 entries and the link is no longer than 100 characters THE SYSTEM SHALL produce a primary `draft_url()` within `MAX_BUTTON_URL_CHARS` that carries the full structured body (no fallback).
- IF the full-body URL exceeds `MAX_BUTTON_URL_CHARS` THEN THE SYSTEM SHALL keep the existing fallback: return a short URL whose body is `Source: <link>` (title truncated to 120 characters if still too long), and return the full structured body as `full_body_if_fallback`.
- WHEN `render_digest()` builds the keyboard THE SYSTEM SHALL keep emitting rows of exactly `{"text": "Draft spike N", "url": ...}` and `{"text": "Create spike N", "callback_data": "scout:create:N"}`.
- IF any required section heading is removed from the scaffold THEN THE SYSTEM's unit tests SHALL fail.

## Out of scope
- Changes to the org issue form `.github/ISSUE_TEMPLATE/spike.yml`, or any write to another repository.
- Changes to mctl-agent's `scout:create:N` handler or SpikeDefinition lifecycle semantics.
- Making the scaffold item-specific (for example, model-generated experiment text). The scaffold is static prose around the existing scored fields.
- Changes to scoring prompts, the `spike:scout` label, dedupe logic or the `MAX_BUTTON_URL_CHARS` value.

## Open questions
- Which prose to use: the issue's example scaffold is about 1,190 characters (about 1,320 URL-encoded). Combined with long but valid header fields, that exceeds the 2000-character button limit for most items, so "Create spike" would produce `Source:`-only issues. This proposal shortens the prose to about 670 characters and keeps every section, which the issue explicitly allows ("The exact prose may be shortened"). The reviewer should confirm the shortened wording.
- From this repository, it is not possible to verify whether mctl-agent's `scout:create:N` handler creates the issue from the URL button's body (so a fallback item would become a `Source:`-only issue). The code comment in `render_digest()` says it reads the draft back from the URL button. The proposal assumes this and therefore keeps the scaffold within the URL budget.
- Documenting section vocabulary for the manual form: no copy of `spike.yml` exists in this repo (`.github/ISSUE_TEMPLATE/` is absent). The proposal adds a short note in `docs/operations/scout.md` only.

# Design: issue-1159-prometheus-pushgateway-is-scraped-twice

## Current state

The pushgateway and everything that scrapes it live in the `monitoring`
ArgoCD Application, `platform-gitops/bootstrap/templates/observability/monitoring.yaml`.
That Application is multi-source; two of its git sources matter here:

```
- path: platform-gitops/infra-components/observability/vm-rules
- path: platform-gitops/infra-components/observability/pushgateway
```

and its sync policy is `automated: {prune: true, selfHeal: true}` with
`ServerSideApply=true`, `ApplyOutOfSyncOnly=true`,
`RespectIgnoreDifferences=true`. Deleting a manifest from either path therefore
deletes the live object on the next sync; no `ignoreDifferences` entry covers
VictoriaMetrics scrape kinds.

**The workload.** `pushgateway/pushgateway.yaml` defines the Deployment
(`prom/pushgateway:v1.10.0`, container port `9091`, unnamed) and a ClusterIP
Service that deliberately carries the label `app: prometheus-pushgateway` and
a **named** port `http` (9091 -> 9091). Its header records why: the previously
out-of-band Service had neither, so the scrape selected nothing.

**Scrape object 1 — the Service path.**
`pushgateway/servicescrape.yaml` is a `VMServiceScrape` selecting
`app: prometheus-pushgateway` in namespace `monitoring`, one endpoint
`port: http`, `honorLabels: true`, no `interval` (so it inherits the
vmagent-wide `scrapeInterval: 1m` set in `monitoring.yaml`). vmagent runs with
`selectAllByDefault: true`, so no `release:` label is needed for selection.
This produces the pool `serviceScrape/monitoring/prometheus-pushgateway/0`.

**Scrape object 2 — the Pod path.**
`vm-rules/pushgateway-podscrape.yaml` is a `VMPodScrape` selecting the same
`app: prometheus-pushgateway` label on the **Pod**, with
`podMetricsEndpoints: [{targetPort: 9091, path: /metrics, interval: 30s,
honorLabels: true}]`. Its header states plainly that it exists to bypass an
unlabelled Service — a condition that the gitops-managed Service in
`pushgateway/pushgateway.yaml` fixed. This produces the pool
`podScrape/monitoring/prometheus-pushgateway/0`.

Both pools are `up` against `http://<pod-ip>:9091/metrics`. Because both set
`honorLabels: true` (correctly — the pushed `job`/`instance` must survive), the
two copies of each pushed metric are distinguished only by vmagent's own
`endpoint` label (`"http"` vs `"9091"`) and by the `service` label that only
the serviceScrape adds.

**Who consumes the duplicated series.** Every rule below matches both copies
because none of them aggregates:

- `vm-rules/backup-alerts.yaml`: `VictoriaMetricsBackupStale`
  (`time() - vmbackup_last_success_timestamp_seconds{job="vmbackup"} > 90000`,
  `for: 10m`) and `VictoriaMetricsBackupMetricAbsent`
  (`absent(vmbackup_last_success_timestamp_seconds{job="vmbackup"})`, `for: 2h`).
- `vm-rules/mctl-telegram-canary.yaml`: `MctlTelegramCanaryStale`
  (`time() - push_time_seconds{job="mctl_telegram_canary"} > 1500`),
  `MctlTelegramCanaryTokenExpiring`, `MctlTelegramCanaryTokenRenewalFailing`;
  plus `MctlTelegramCanaryFailing` (`max_over_time(...[25m]) == 0`) and
  `MctlTelegramCanaryAbsent` (`absent_over_time(...[30m])`), which are affected
  differently but still evaluate over doubled series.

All of these route to the `mctl-agent` receiver
(`monitoring.yaml`, the `alertname =~ ".*|MctlTelegramCanary.*"` route), which
opens an incident per notification — so one fact becomes two incidents.

**Why nobody noticed.** The podScrape does not live next to the thing it
scrapes; it sits in `vm-rules/`, a directory of `VMRule` objects consumed by
`scripts/check-vm-rules.sh`. That script iterates `*.yaml`, reads `.kind`, and
for anything that is not a `VMRule` prints `skip (kind=VMPodScrape)` and moves
on. It is currently the only non-`VMRule` file there (verified: the other
eleven are all `kind: VMRule`). Neither scrape file mentions the other.

## Proposed solution

Delete the pod-level scrape; keep the Service-level one; move its history into
the survivor; close the door that let it hide.

**1. Delete `platform-gitops/infra-components/observability/vm-rules/pushgateway-podscrape.yaml`.**

The `VMServiceScrape` is the conventional path in this repo (every other
scrape object under `bootstrap/templates/mctl-platform/*-monitor.yaml` and
`argo-workflows/config/servicemonitor.yaml` is Service-level), it is
demonstrably `up`, and it is co-located with the Deployment and Service it
depends on — so a future edit to the Service's label or port name is visible in
the same directory as the scrape that relies on it. The podScrape is the one
whose stated reason for existing is gone.

ArgoCD prunes the live `VMPodScrape` automatically (`prune: true` on the
`monitoring` Application). vmagent's operator-generated scrape config is
regenerated by the VictoriaMetrics operator when the object disappears; no
vmagent restart is needed.

**2. Fold the podScrape's history into `pushgateway/servicescrape.yaml`.**

The deleted header carries two facts worth keeping and one worth adding:

- *Why a pod-level scrape once existed*: the live Service had no labels and an
  unnamed port, so the Service path selected zero targets and
  `MctlTelegramCanaryAbsent` fired perpetually even while the canary pushed
  successfully. That is fixed in `pushgateway.yaml`, and the fix is what makes
  this deletion safe.
- *Why `honorLabels: true` is load-bearing*: the pushed `job`/`instance` labels
  must survive, because `MctlTelegramCanaryStale` keys off
  `push_time_seconds{job="mctl_telegram_canary"}` and the backup rules key off
  `{job="vmbackup"}`. Without it the scrape would overwrite `job` with the
  scrape's own job name and every one of those rules would silently go
  `absent`.
- *New*: this is the ONLY scrape of the pushgateway, deliberately. A second one
  (Pod- or Service-level) duplicates every pushed series and doubles every
  alert on it — issue #1159. If the Service path ever breaks again, fix the
  Service; do not add a parallel scrape.

This is consistent with how this repo already documents reversals — the
`ignoreDifferences` block in `monitoring.yaml` and the `trap`/cleanup comment
in `check-vm-rules.sh` both explain removed things in place.

**3. Make `scripts/check-vm-rules.sh` fail on a non-`VMRule` under `vm-rules/`.**

Change the `skip (kind=$kind)` branch from `continue` to an error that sets
`fail=1` and emits a `::error file=...::` annotation, matching the style the
script already uses for a failed `promtool check`. After step 1 every file in
that directory is a `VMRule`, so this is green on day one and is the only
mechanism that stops the exact recurrence: an object of the wrong kind parked
in a rules directory where nothing looks at it. `.github/workflows/validate-manifests.yml`
already runs this script as the "Check and unit-test alerting rules" step, and
separately kubeconform-validates all of `platform-gitops/infra-components`, so
a legitimately-placed scrape object under `pushgateway/` is still schema-checked.

**What is explicitly NOT changed:** the scrape's `honorLabels: true`, the
Service, the Deployment, and every alert expression. The surviving scrape gains
no `interval`, so the gateway is scraped at vmagent's 1m default rather than
the podScrape's 30s. Every consumer tolerates that by a wide margin (smallest
threshold: 1500s of push staleness; smallest window: `[25m]`), and the gateway
is a cache of values pushed every 10 minutes at the fastest.

## Alternatives

**A. Keep the `VMPodScrape`, delete the `VMServiceScrape`, and move the
podScrape into `observability/pushgateway/`.** Equally correct on the
duplication axis and preserves the 30s interval. Dropped because the Service
path is the repo-wide convention, the Service already exists and is maintained
for this purpose (so keeping the podScrape means keeping a Service nothing
scrapes), and pod-level scraping loses the `service` label and re-breaks
whenever the deployment shape changes. It also throws away the one thing the
2026-05-25 fix bought: a labelled, named-port Service.

**B. Keep both scrapes and aggregate the alert expressions
(`max by (job, instance) (...)`).** Explicitly rejected by the issue, and
correctly: it treats every current and future rule over a pushed metric as the
place to compensate for a configuration mistake, leaves the doubled sample
rate and the redundant 30s scrape in place, and fails silently the first time
someone writes a new rule without remembering the convention.

**C. Keep both scrapes and drop the `endpoint` label on one via
`metricRelabelConfigs`, letting VictoriaMetrics deduplicate identical series.**
Makes the two scrapes write the same series and relies on VM's dedup window to
collapse them. Dropped: it is strictly more configuration to achieve what a
deletion achieves, dedup across two independent scrapers with different
intervals (30s vs 60s) is timing-dependent rather than guaranteed, and it still
costs two scrapes and two remote-write streams.

## Platform impact

- **Migrations / backward compatibility.** None in the schema sense. Series
  carrying `endpoint="9091"` (and no `service` label) stop receiving samples at
  the sync. Historical samples remain in VictoriaMetrics until retention
  expires; Grafana panels are unaffected — no dashboard under
  `infra-components/observability/grafana-dashboards/` selects on `endpoint`
  (verified by grep).
- **Alerting during the cutover.** The abandoned duplicate series goes stale
  after VM's default lookbehind (~5m) and simply stops matching, long before
  1500s (`MctlTelegramCanaryStale`) or 90000s (`VictoriaMetricsBackupStale`) of
  apparent staleness could accumulate. `absent()`/`absent_over_time()` rules
  still see the surviving copy throughout, so they cannot fire from this change.
  Expected observable effect: alert *counts* halve; alert *states* do not
  change.
- **Resource impact.** One fewer scrape of a small target every 30s, and half
  the ingested samples for everything routed through the gateway. Marginal,
  but in the right direction for vmagent, which was CPU-throttled recently
  enough that its limit was raised 250m -> 500m (comment in `monitoring.yaml`).
- **Risk: the surviving scrape breaks and nothing scrapes the gateway.** This
  is the real risk of going from two to one. Mitigated three ways: the Service
  label and port name are in gitops with a comment explaining that the scrape
  depends on them; `ScrapePoolHasNoTargets` for `namespace = "monitoring"` is
  routed to the `mctl-agent` receiver in `monitoring.yaml` and is exactly the
  alert that caught the original breakage; and `VictoriaMetricsBackupMetricAbsent`
  / `MctlTelegramCanaryAbsent` fire independently if pushed metrics stop
  arriving. Verification (task T1) checks the surviving target is `up` before
  the change is called done.
- **Risk: CI regression from the `check-vm-rules.sh` change.** Bounded — it
  only fires on a non-`VMRule` file inside `vm-rules/`, and after this change
  there are none. The failure message should name the correct destination
  (`infra-components/observability/<component>/`) so the next person is not
  merely blocked.
- **Rollback.** Restoring the deleted file re-creates the object within one
  ArgoCD sync; there is no data migration to undo.

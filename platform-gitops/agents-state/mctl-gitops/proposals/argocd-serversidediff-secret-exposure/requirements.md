# Confirm/patch Argo CD version against ServerSideDiff cleartext-Secret CVEs

## Context
CVE-2026-43824 and CVE-2026-42880 (both CVSS 9.6) allow a read-only Argo CD
user, or the ServerSideDiff code path itself, to read cleartext Kubernetes
Secret data that should be masked. The affected ranges are Argo CD
3.2.0–3.2.11 and 3.3.0–3.3.9. This platform relies on Argo CD as the sync
engine (`ops.mctl.ai`) reconciling manifests from this repo, and on
ExternalSecrets Operator + Vault to render the very Secret objects that
would be exposed by this flaw — a leak here directly undermines the
"no hardcoded secrets, all via Vault + ExternalSecrets" convention in
`context/architecture.md`.

`context/current-version.md` does not pin an exact deployed Argo CD build,
only the `mctl-gitops` repo tag (4.10.1). The researcher's own latest-release
scan shows Argo CD v3.5.2 as current upstream, which postdates the fix
versions. The actionable work is therefore to verify the deployed Argo CD
version against the affected ranges and, if it falls inside them, pin the
`apps` ApplicationSet's controller/repo-server images to a patched minor
(>=3.2.12 or >=3.3.10, or the already-current 3.5.2 line) — a version-pin
change, not an architecture or pattern change, so it does not conflict with
ADR-0001.

## User stories
- AS a platform operator I WANT confirmation of the deployed Argo CD version
  against CVE-2026-43824/CVE-2026-42880 SO THAT I know whether tenant
  Secrets are currently exposable via ServerSideDiff.
- AS a tenant with read-only Argo CD access I WANT the platform to run a
  patched Argo CD version SO THAT I cannot accidentally or maliciously read
  other tenants' cleartext Secret data.
- AS the mctl-gitops maintainer I WANT the version pin recorded in this repo
  SO THAT future audits can confirm the fix without re-checking upstream.

## Acceptance criteria (EARS)
- WHEN the spec-writer/operator inspects the deployed Argo CD image tag THE
  SYSTEM SHALL report whether it falls inside 3.2.0-3.2.11 or 3.3.0-3.3.9.
- IF the deployed version falls inside an affected range THEN THE SYSTEM
  SHALL be pinned to a patched version (>=3.2.12, >=3.3.10, or a later minor
  such as 3.5.2) in the ArgoCD bootstrap/apps manifests in this repo.
- WHEN the Argo CD version pin is changed THE SYSTEM SHALL apply it only to
  the Argo CD control-plane component (server/controller/repo-server
  images), not to the ApplicationSet pattern or Application API version.
- WHILE the version pin is in place THE SYSTEM SHALL continue to reconcile
  all existing Applications generated by the `apps`, `tenants`, and
  `openclaw-skills` ApplicationSets without manual re-sync.
- IF the currently deployed version is already patched (e.g. already on
  3.5.x) THEN THE SYSTEM SHALL record that confirmation in this repo instead
  of performing an unnecessary version bump.

## Out of scope
- Any unrelated Argo CD major-version upgrade (e.g. jumping to a new major
  line) not required to close these CVEs.
- Changes to the ApplicationSet pattern, App-of-Apps structure, or adding
  approval gates around sync (excluded per ADR-0001).
- Auditing or rotating Secrets that may have already been exposed prior to
  this patch — that is an incident-response action, tracked separately if
  evidence of exploitation is found.

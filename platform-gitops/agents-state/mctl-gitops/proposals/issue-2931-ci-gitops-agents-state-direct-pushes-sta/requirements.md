# Stop mctl-agents state writes starving GitOps Merge Queue — revision 3

## Decision and problem statement

**Owner decision (2026-11-23, mctl-gitops#2931): GO_RESEARCH / DESIGN for options 2 + 4.** The target is a separately permissioned repository, provisionally `mctlhq/mctl-agents-state`, for agent-generated proposal and operational state; merge-queue starvation monitoring is required. This is **not** approval to implement, merge or deploy. The separate-repository migration is **in scope**, not a follow-up. Batch commits, increased queue parallelism and queue-aware push deferral are not substitutes.

Observed 2026-11-22: many `chore(agents)` direct commits to `mctl-gitops/main` invalidated merge-group heads (#2923), blocked #2924/#2927, and triggered numerous heavyweight `validate-manifests.yml` push jobs across the organization's shared GitHub-hosted runner quota. See #2931 evidence and follow-up comment on hosted runners, plus mitigation PR #2935 (MERGED 2026-11-23 01:22 UTC). A red workflow alone is not a reliable page to the operator. We must eliminate direct agent-state pushes to `mctl-gitops/main` and provide actionable alerts, while preserving content-bound human approval.

## Scope and invariants

1. **Canonical target:** migrate agent runtime state and generated proposal artifacts currently under `platform-gitops/agents-state/**` into a **separate** repository. Keep `mctl-gitops/main` only for GitOps desired-state declarations, workflows and migration configuration. No automated agent status write may advance `mctl-gitops/main` after cutover.
2. **Trust separation:** proposal content (`requirements.md`, `design.md`, `tasks.md` and optional `proposed-content.md`) is reviewable and immutable for a given approved revision; operational `.status.yaml`, attempts, review status and inbox are mutable. The design SHALL explicitly isolate bots that publish runtime status from the protected review/approval source and define its branch/ruleset design. A repository-scoped key alone is not path-scoped.
3. **Approval invariants:** no agent write is an owner approval; no missing, anonymous, mismatched or stale `approval.approved_by` / `approval.content_digest` may enable implementation. `control.requires_human_approval` stays fail-closed. Review grants bind to exact content digest, proposal identity and immutable Git revision, and are invalidated by amendment or migration drift.
4. **No automatic authority expansion:** no admin bypass, no Merge Queue bypass, no automatic owner approval, no implementer start from this design authorization. Existing writers remain functioning until explicit phased rollout / evidence / rollback approval.
5. **No duplicate work:** linked #2543 deploy-key hardening and PR #2935 push-run concurrency cancellation are dependencies or adjacent mitigations, not new implementation issues; `mctl-gitops#2931` owns the migration proposal.

## User stories

- AS an operator I WANT workflows to record status during a DevLoop burst without writing to `mctl-gitops/main` SO THAT valid queued pull requests can complete checks.
- AS an approver I WANT review grants bound to exactly the immutable proposal I saw SO THAT migrations, retries, races and amendments cannot cause unreviewed implementation.
- AS a security maintainer I WANT the runtime writer's credential limited to an isolated repository and branch SO THAT a stolen agent deploy credential cannot advance GitOps desired state.
- AS an on-call operator I WANT 3-rebuild, 15-minute no-progress and causal push alerts SO THAT I can act before the 120-minute queue eviction.
- AS a workflow maintainer I WANT measured cutover, idempotent writes, reconciliation and a tested rollback SO THAT operational status is never silently lost or duplicated.

## Acceptance criteria (EARS)

### Repository and migration

- R1. WHEN migration is activated THE SYSTEM SHALL use a separately provisioned `mctlhq/mctl-agents-state` repository (or an explicitly owner-approved equivalent); `mctl-gitops/main` SHALL no longer receive writes of `platform-gitops/agents-state/**` by agent workflows. A branch *within mctl-gitops* does **not** satisfy this criterion.
- R2. BEFORE cutover THE SYSTEM SHALL inventory **every** reader, writer, poller, validator, CLI, API and workflow referring to `agents-state` or its GitHub source/ref, with repository/path/evidence, owner, transition mode and validation test; an unknown consumer blocks GO_CUTOVER.
- R3. BEFORE activating the new state store THE SYSTEM SHALL keep approval-bearing proposal content (the existing four-file digest input) on an immutable, reviewed source whose write permissions are technically disjoint from the operational-state writer. The candidate design is a protected `specs` ref, but it SHALL NOT be selected unless effective GitHub rules, repository visibility and credentials have passed negative authorization tests. A `runtime` bot must never rewrite reviewed content or impersonate the reviewer.
- R4. WHEN a proposal that **requires human approval** transitions to an executable accepted state THE SYSTEM SHALL validate the audited owner grant against proposal identity, byte-exact content digest, immutable reviewed ref/SHA, named approver and migration epoch. `status: accepted` alone SHALL NOT grant authority: existing legacy incident records without verifiable grants remain visible as accepted-but-quarantined and unrunnable. Replays SHALL NOT start implementation twice.
- R5. WHEN any workflow writes proposal/runtime state THE SYSTEM SHALL use optimistic ref compare-and-swap (or equivalent conditional update), bounded retries/backoff, a stable command/idempotency key and a durable transition result. When the operation conflicts, it SHALL re-read authoritative state, revalidate the transition and avoid last-write-wins; a lost/uncertain write SHALL be surfaced as `unknown/pending_reconciliation`, not success.
- R6. WHEN a new repository, ref, credential, or required approval source is unavailable THE SYSTEM SHALL expose explicit retriable/unavailable status and SHALL NOT report success, silently reconstruct a grant, or fall back to pushing `mctl-gitops/main`. In the new migration epoch, a missing legacy directory or un-upgraded API reader SHALL NOT convert outstanding `human-input/request.json` records into an empty successful listing.
- R7. BEFORE switching writers THE SYSTEM SHALL complete a checksum/inventory backfill, prove source-to-target parity, run shadow reads and conflict/replay tests, and verify an owner-defined maximum freshness lag. The cutover SHALL be gated by an explicit independent review plus separate owner GO_CUTOVER.
- R8. DURING migration THE SYSTEM SHALL keep an auditable mapping of old path/commit/SHA to proposal identity, new immutable specs ref/SHA, runtime ref, and grant/transition ID. A live DevLoop or pending decide-page link bound to the old epoch SHALL either resolve to exactly the same signed/digested authority after audited reconciliation or fail closed; no automatic rebinding/approval is allowed.
- R9. WHEN rollback is declared THE SYSTEM SHALL support a tested reader/writer rollback or pause with reconciliation and without re-enabling unsafe direct pushes. Rollback SHALL preserve approved digest and attempt/approval history; non-reversible states must cause a fail-closed operator hold.

### Legacy and distributed approval safety

- R19. BEFORE migration THE SYSTEM SHALL classify each legacy proposal as `proposed`, `accepted+verified grant`, `accepted+unverified/anonymous grant`, `accepted+legacy auto-accepted incident`, `in-progress/attempt leased`, or `terminal`; preserve recorded display status and provenance; quarantine every unverified category from new execution. `control.requires_human_approval: false` or an absent control block SHALL NEVER create execution authority by itself.
- R20. WHEN a grant is issued, consumed, or retried THE SYSTEM SHALL record a stable transition/operation ID and resolve the outcome against the authoritative grant ledger, Temporal/Argo submission evidence and the repository's durable state ref. No network timeout, CAS conflict or partial failure SHALL silently produce an approved-and-runnable record. Re-issue or refund of an uncertain consumed grant SHALL require a formally defined, audited recovery decision, not an automatic fallback.
- R21. WHEN `human-input/request.json`, inbox, incidents or proposal attachments are copied THE SYSTEM SHALL classify and prevent exposure of personal/sensitive payloads, enforce authorized readers and retention/erasure policy, and use a private-compatible security topology. Absence of effective private-branch protections is a blocker, **not** permission to publish the state repository publicly.
- R22. WHEN a migration-epoch reader cannot distinguish a genuinely empty state tree from a missing/unmigrated source or unauthorized GitHub access THE SYSTEM SHALL return a typed `unknown/unavailable` and alert, not `[]`/200 or a 'no pending human input' claim.

### Permissions and security

- R10. THE SYSTEM SHALL use least-privilege, independently scoped GitHub credentials for runtime status, reviewed proposal publication and GitOps configuration. A negative authorization test SHALL prove runtime identity cannot update `mctl-gitops/main`, protected specs, force-push or delete refs. Default visibility SHALL be private for potentially sensitive operational/human-input data unless classified otherwise; if branch protections cannot be effectively enforced for the chosen private repository/account tier, the architecture SHALL require a mediated writer or separately protected authority store before GO_IMPLEMENT. Retire old P6 deploy-key bypass via #2543 only after proven safe cutover.
- R11. THE SYSTEM SHALL protect force-pushes, branch deletion and unreviewed approval-material edits; map GitHub App / deploy-key repository-level capabilities, ruleset bypass actors, and CI enforcement with tests of effective permissions, not merely template `git add` path guards.
- R12. THE SYSTEM SHALL preserve `proposal_id → reviewed specs SHA/digest → authenticated owner grant → grant lifecycle/command ID → durable status transition → implementation attempt/PR` across stores. Because the mctl-api grant is consumed before Argo submit and Git state is committed separately, the design SHALL specify durable recovery for spent-but-unsubmitted, submitted-but-uncommitted, and committed-but-unconfirmed outcomes; missing/ambiguous reconciliation SHALL block execution.

### Queue and CI observability

- R13. WHEN a queue entry is rebuilt at least **3 times** without progressing THE SYSTEM SHALL emit a deduplicated actionable alert naming head PR, affected queued PRs, original and rebuilt merge-group SHA(s), offending push SHA, bot identity and workflow correlation (or explicitly `unknown` when attribution is unavailable).
- R14. WHEN entries wait but **no meaningful queue progress occurs for 15 minutes** THE SYSTEM SHALL alert; age alone is not equivalent to progress. Monitoring SHALL distinguish healthy long-running checks from repeated invalidation and shall have an explicit false-positive policy.
- R15. WHEN a bot push to a protected branch invalidates merge-group checks THE SYSTEM SHALL correlate the push with invalidated runs where evidence supports causality and alert, including after the migration; non-causal temporal coincidence must be qualified.
- R16. WHEN monitoring cannot read authenticated merge-queue/check-run data or its scheduled execution misses its service interval THE SYSTEM SHALL emit `unknown/monitoring-degraded` and notify the on-call route instead of green; schedule target is ~5 minutes, with a 15-minute *lack of meaningful progress* threshold. Every alert SHALL carry evidence provenance (API URL/fixture timestamps/check SHA), an attribution confidence field, and a recovery/dedup rule.
- R17. BEFORE implementing merge-queue monitoring THE SYSTEM SHALL demonstrate actual GitHub GraphQL/REST fields, privileges, pagination, rate limiting and runner-job query behavior using read-only, source-pinned fixtures; tests SHALL cover empty queue, 3 rebuilds, 15-minute stalled progress, a healthy long check, stale queue SHA, 403/404/429/5xx, missing permissions, monitor missed schedules, and uncertain bot-push causality.
- R18. BEFORE declaring success THE SYSTEM SHALL verify the bot-generated `push` workload drops from GitOps `main`, stale CI runs are canceled or bounded (respect #2935), merge-group jobs finish in at least one representative synthetic DevLoop burst, and unrelated repositories do not suffer the same hosted-runner starvation.

## Exclusions

- No implementation in this revision; these are design and acceptance documents only.
- No wholesale changes to release image bumps, GitOps desired state or queue-policy bypass.
- Queue-aware deferral is an optional short-lived mitigation only if separately justified with expiry, risk, proof of no approval latency regression, and its own GO. It cannot satisfy R1 or R10, and is not part of the required end state.
- Do not change `max_entries_to_build` or queue timeout as the primary repair; settings may be evaluated separately after evidence.

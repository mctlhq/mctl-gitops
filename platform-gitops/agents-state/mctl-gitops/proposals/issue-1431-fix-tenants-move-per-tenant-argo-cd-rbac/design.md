# Design: issue-1431-fix-tenants-move-per-tenant-argo-cd-rbac

## Current state

**Where the policy lives.** Argo CD's RBAC is one Helm value:
`platform-gitops/argocd/values.yaml` → `argo-cd.configs.rbac`, with
`policy.default: ""` (line 175), `scopes: "[groups]"` (line 176) and a single
multi-line `policy.csv` block (lines 177-241). That block holds three different
kinds of rule:

- the platform base: `role:admin` (including the only `exec` grant, lines 179-185)
  and the `mctl-api` / `ci-freshness` service accounts (lines 197-200);
- five per-tenant blocks: `labs` (205-211), `yyy` (213-219), `xxxx` (221-226),
  `ovk` (227-233), `karabu` (235-241). Each is `applications get/list/sync/override`
  plus `logs get` on `apps/<tenant>-*`, then `g, <tenant>, role:team-<tenant>`.
  `yyy` and `xxxx` have no `platform-gitops/tenants/` directory and no
  `platform-gitops/services/` directory — they are orphans left by deleted tenants,
  and `xxxx` does not even carry the `# Tenant:` comment the `sed -i` cleanup keys
  on;
- a comment recording the SOC F4 control ("Tenant roles: no exec", lines 202-204).

The ConfigMap itself is rendered by the vendored subchart,
`platform-gitops/argocd/charts/argo-cd-9.5.9.tgz` →
`templates/argocd-configs/argocd-rbac-cm.yaml`. That template is gated on
`.Values.configs.rbac.create` (default `true`, documented in the chart's values as
"If false, it is expected the configmap will be created by something else") and it
emits `data: {{ toYaml (omit .Values.configs.rbac "create" "annotations") }}` — so
whatever keys sit under `configs.rbac` become CM keys verbatim. The chart is applied
by the `argocd-self-managed` Application
(`platform-gitops/argocd/templates/argocd-self-managed.yaml`): `path:
platform-gitops/argocd`, `valueFiles: [values.yaml]`, `prune: false`,
`selfHeal: true`, `ServerSideApply=true`.

**Who writes it.** `platform-gitops/argo-workflows/cluster-templates/wft-create-tenant.yaml`,
step `commit-tenant-to-git`, section "Append ArgoCD RBAC entries": it builds
`RBAC_BLOCK` from `${TENANT}` and inserts it with

```
awk -v rbac="$RBAC_BLOCK" '/^    secret:/ { print rbac } { print }' "$ARGOCD_VALUES"
```

then `git add`s `platform-gitops/argocd/values.yaml` together with the tenant's own
`platform-gitops/tenants/${TENANT}/{values,catalog-info}.yaml` and
`platform-gitops/argo-workflows/sso-team-${TENANT}.yaml`. The push loop
(`MAX_ATTEMPTS=5`) responds to a rejected push with `git fetch` + `git rebase
origin/main`; the whole script is `set -e`, so the content conflict on the shared
anchor aborts the step on attempt 1 with the rebase left in progress.

`wft-delete-tenant.yaml` (lines 212-218) and `wft-delete-tenant-safe.yaml`
(lines 555-561) do the inverse with four `sed -i` expressions plus a blank-line
squeeze. Everything else these steps write is already per-tenant:
`platform-gitops/tenants/<t>/`, `argo-workflows/sso-team-<t>.yaml`,
`platform-skills/bindings/tenants/<t>.yaml`,
`services/<t>/openclaw/generated/platform-skills-values.yaml`. The exceptions are
the CNPG shared files (`infra-components/data/cnpg/shared/{databases,secrets,
cluster}.yaml`), edited by the delete templates only.

**Relevant conventions found in the clone.** `.github/workflows/validate-manifests.yml`
already runs a long series of `scripts/validate-*.py` gates, each invoked
`--selftest` first with an in-file comment explaining that "a detector that has
never been seen to fire is not known to work"
(`validate-shell-param-interpolation.py`, `validate-yq-interpolation.py`,
`validate-openclaw-version-pin.py`, `validate-implement-worker-singleton.py`, …).
It also runs `scripts/materialize-openclaw-platform-skills.py --check`, a
generated-file drift gate. The same job already does `helm lint
platform-gitops/argocd` and `helm template test platform-gitops/argocd -f
platform-gitops/argocd/values.yaml | kubeconform`. This proposal reuses both
patterns rather than inventing a new gate style.

Also relevant: every service Application is created by
`platform-gitops/bootstrap/templates/bootstrap/applicationset-apps.yaml` with
`project: apps` hardcoded, and app names are `<tenant>-<service>` — which is why the
policy globs read `apps/<tenant>-*` (project `apps`, app prefix `<tenant>-`).

## Proposed solution

Split `policy.csv` into a base part that stays in `values.yaml` and one CSV
fragment per tenant, and move the assembly into this repo's own chart.

### 1. Per-tenant fragment files

New directory inside the `argocd-config` chart:

```
platform-gitops/argocd/rbac/tenants/labs.csv
platform-gitops/argocd/rbac/tenants/ovk.csv
platform-gitops/argocd/rbac/tenants/karabu.csv
```

Each file is exactly the six canonical lines for that tenant, unchanged from what
`values.yaml` holds today, e.g. `labs.csv`:

```
# Tenant: labs — generated by wft-create-tenant. No exec (SOC F4).
p, role:team-labs, applications, get, apps/labs-*, allow
p, role:team-labs, applications, list, apps/labs-*, allow
p, role:team-labs, applications, sync, apps/labs-*, allow
p, role:team-labs, applications, override, apps/labs-*, allow
p, role:team-labs, logs, get, apps/labs-*, allow
g, labs, role:team-labs
```

The directory must live **under the chart root** (`platform-gitops/argocd/`)
because Helm's `.Files` cannot escape the chart directory, and the Argo CD
repo-server renders the chart with `path: platform-gitops/argocd`. A fragment path
is a pure function of the tenant name, so two concurrent creates write two
different paths and git merges them with no conflict; a delete is a `git rm` of one
file, which by construction leaves no stray comment or blank line behind.

### 2. The chart owns `argocd-rbac-cm`

In `platform-gitops/argocd/values.yaml`, set `argo-cd.configs.rbac.create: false`
and delete the five tenant blocks from `policy.csv`, leaving the base policy
(admin, `mctl-api`, `ci-freshness`) and the SOC F4 comment in place. Add
`platform-gitops/argocd/templates/argocd-rbac-cm.yaml`:

```yaml
{{- /*
  argocd-rbac-cm is rendered here, not by the argo-cd subchart
  (configs.rbac.create: false), so that each tenant's policy lines can live in
  its own file — rbac/tenants/<tenant>.csv — instead of in this chart's shared
  values.yaml. Two concurrent wft-create-tenant runs then write disjoint paths
  and never conflict in git (issue 1431).
  Fragments are concatenated into the single policy.csv key rather than emitted
  as separate policy.<tenant>.csv keys: Argo CD merges extra policy keys, but a
  single key keeps the rendered policy byte-comparable with the pre-migration
  one and independent of that feature.
*/ -}}
{{- $rbac := index .Values "argo-cd" "configs" "rbac" -}}
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: {{ .Release.Namespace }}
  labels:
    app.kubernetes.io/name: argocd-rbac-cm
    app.kubernetes.io/part-of: argocd
    app.kubernetes.io/component: rbac-cm
data:
  policy.default: {{ index $rbac "policy.default" | default "" | quote }}
  scopes: {{ index $rbac "scopes" | quote }}
  policy.csv: |
    {{- index $rbac "policy.csv" | trim | nindent 4 }}
    {{- range $path, $content := .Files.Glob "rbac/tenants/*.csv" }}
    {{ printf "# %s" $path }}
    {{- $content | toString | trim | nindent 4 }}
    {{- end }}
```

`range` over the map returned by `.Files.Glob` iterates keys in sorted order, so
the render is deterministic. Order has no semantic effect anyway: the policy
contains only `allow` rules and `policy.default` is `""`, so casbin evaluation is
order-independent. An empty `rbac/tenants/` still renders a valid ConfigMap holding
just the base policy. `argocd-server` reloads `argocd-rbac-cm` in place, so no
restart is needed.

### 3. Workflow templates stop touching shared files

`wft-create-tenant.yaml`, `commit-tenant-to-git`: replace the "Append ArgoCD RBAC
entries" section with a per-tenant file write, keeping the existing idempotency
behaviour (the current code skips when `role:team-${TENANT},` is already present;
the new code skips when the file exists), and drop
`platform-gitops/argocd/values.yaml` from the `git add` list:

```sh
RBAC_FILE="platform-gitops/argocd/rbac/tenants/${TENANT}.csv"
if [ -f "$RBAC_FILE" ]; then
  echo "WARNING: ArgoCD RBAC fragment for ${TENANT} already exists, skipping."
else
  mkdir -p platform-gitops/argocd/rbac/tenants
  cat > "$RBAC_FILE" <<EOF
# Tenant: ${TENANT} — generated by wft-create-tenant. No exec (SOC F4).
p, role:team-${TENANT}, applications, get, apps/${TENANT}-*, allow
...
g, ${TENANT}, role:team-${TENANT}
EOF
fi
git add ... "$RBAC_FILE"
```

`${TENANT}` is safe both as a path component and as file content: the
`validate-tenant-name` step of the same workflow enforces
`^[a-z0-9][a-z0-9-]{0,62}$` (`tpl-validate-tenant.yaml` line 68), and the value
reaches this script through `PARAM_TENANT_NAME` in the environment, never by Argo
interpolation, per the security note already at the top of the step.

Both delete templates replace their four `sed -i` calls with

```sh
RBAC_FILE="platform-gitops/argocd/rbac/tenants/${TENANT}.csv"
if [ -f "$RBAC_FILE" ]; then git rm "$RBAC_FILE"; CHANGED=true; fi
```

and the commit-message lines change from "Removed ArgoCD RBAC for
role:team-${TENANT}" to name the removed file.

### 4. Two CI gates

`scripts/validate-tenant-workflow-shared-writes.py` (new, `--selftest` first, in
the existing style): parse the three tenant workflow templates, pull out every
`script.source` body, and collect every repository path that appears in a write
position — `cat > P`, `> P`, `sed -i ... P`, `awk ... > P`, `git add P`,
`git rm P`, `mkdir -p P`, including via a `VAR="path"` assignment that is later
used in one. Fail unless each such path either contains `${TENANT}` /
`${PARAM_TENANT_NAME}` or appears in a module-level `WAIVERS` table with a comment
and an issue reference (initially the three CNPG shared files). `--selftest`
rebuilds the old `awk`-into-`platform-gitops/argocd/values.yaml` block in a
throwaway template and asserts the detector fires on it, and asserts it does *not*
fire on the post-change template — this is the regression test the issue asks for.

`scripts/validate-argocd-tenant-rbac.py` (new): assert a 1:1 correspondence
between `platform-gitops/tenants/*/` and `platform-gitops/argocd/rbac/tenants/*.csv`,
and that each fragment equals the canonical rendering for its tenant name
(so no extra verb, no widened object glob, and no `exec` can be slipped into a
fragment by hand — the SOC F4 control becomes machine-checked, which
`values.yaml`'s comment never was). Also assert `platform-gitops/argocd/values.yaml`
contains no `role:team-` line at all, so a hand edit cannot quietly reintroduce the
shared-file pattern. `--selftest` covers: an `exec` line, a widened glob, a missing
fragment, an orphan fragment.

Both are wired into `.github/workflows/validate-manifests.yml` next to the existing
`validate-shell-param-interpolation.py` / `validate-yq-interpolation.py` steps.

### 5. Migration and equivalence proof

One atomic commit: create the three fragments, delete the five tenant blocks from
`values.yaml`, flip `create: false`, add the template, edit the three workflow
templates, add the gates. The commit must not be split — `create: false` without
the new template would leave the live ConfigMap unmanaged (`prune: false` on
`argocd-self-managed` means it would *not* be deleted, but it would also stop
tracking git).

Equivalence is proven two ways, both recorded in the PR:

1. Rendered-policy diff: `helm template test platform-gitops/argocd -f
   platform-gitops/argocd/values.yaml`, extract `data["policy.csv"]`, strip
   comments and blank lines, sort, and diff pre- vs post-change. The only expected
   difference is the removal of the six `yyy` and six `xxxx` lines.
2. Live check with `argocd admin settings rbac can <group> <action> <resource>`
   (per the runbook style already used in `docs/soc2/access-review.md`) for each of
   `labs`, `ovk`, `karabu`: the four `applications` verbs and `logs get` allowed on
   `apps/<t>-*`, `exec create` denied, and anything on another tenant's prefix
   denied.

## Alternatives

**A. Per-tenant `AppProject` roles (issue option 1).** Render an `AppProject` per
tenant from the tenant chart with `spec.roles[].groups: [<tenant>]`. Dropped: an
AppProject role can only grant on applications *inside that project*, and every
service Application is created with `project: apps` hardcoded in
`applicationset-apps.yaml`. Adopting it means moving every existing Application to a
new project and duplicating the `apps` project's `clusterResourceWhitelist`,
`namespaceResourceWhitelist`, `orphanedResources` and the live `syncWindows` freeze
on `admins-openclaw` / `ovk-openclaw` into each tenant project — a change whose
failure mode is "apps stop syncing", far past the blast radius this fix needs.
Adding the roles to the *existing* `apps` project instead does not help at all:
`project-apps.yaml` is itself a file shared by all tenants, so the conflict simply
moves.

**B. Separate `policy.<tenant>.csv` keys in `argocd-rbac-cm` (issue option 2).**
Argo CD does merge additional policy keys, but the keys still have to be produced by
whoever owns the ConfigMap, and Helm values cannot be computed from templates — so
this requires the same `create: false` + own-template step as the chosen design and
then adds a dependency on the multi-key feature. Having a *second* Application also
manage keys of the same ConfigMap was rejected outright: two Argo CD Applications
claiming one resource produces a shared-resource warning and a permanent OutOfSync.
The chosen design is option 2's file layout with single-key concatenation, which
keeps the render byte-comparable to today's policy.

**C. Generate `policy.csv` from `platform-gitops/tenants/*/values.yaml` at render
time (issue option 3).** The genuinely single-source-of-truth variant, and the
reason it was dropped is mechanical: `.Files.Glob` cannot read outside the chart
directory, and the `argocd-config` chart is rooted at `platform-gitops/argocd`. The
workarounds are all worse — rooting the chart at `platform-gitops/` would make every
service commit re-render the Argo CD Application, and putting a `Chart.yaml` +
`templates/` inside `platform-gitops/tenants/` would make the tenants
ApplicationSet's `directories: platform-gitops/tenants/*` generator mint a bogus
`tenant-templates` Application. Argo CD multi-source `ref` sources only supply
`valueFiles`, not globbable files. The chosen design recovers what matters from this
option — a single authoritative tenant list — with the 1:1 CI gate in
`validate-argocd-tenant-rbac.py` instead of a second render path.

## Platform impact

**Migration.** Three new files, one changed values file, one new template, three
edited workflow templates, two new scripts, one CI workflow edit. No cluster
resource is created or destroyed: `argocd-rbac-cm` keeps its name and namespace and
stays inside the same `argocd-self-managed` Application, so the sync is an in-place
update. Its labels change (the subchart's `argo-cd.labels` set is replaced by an
explicit three-label set); nothing selects that ConfigMap, and Argo CD finds it by
name.

**Backward compatibility.** Effective policy is unchanged for `labs`, `ovk` and
`karabu`. The orphans `yyy` and `xxxx` are dropped — an intentional reduction, since
`apps/yyy-*` can match no Application (no `platform-gitops/services/yyy/`) and no
tenant directory exists for either. This must be called out in the PR body, because
it is the one line where "effective RBAC unchanged" is deliberately not literal.

**Resource impact.** None. One extra `.Files.Glob` over a handful of small files per
`argocd-config` render; the repo-server already renders this chart on every
Argo CD poll.

**Risks and mitigations.**

- *Total RBAC loss if `create: false` lands without the new template.* Mitigation:
  single atomic commit; `helm template ... | grep argocd-rbac-cm` asserted in CI;
  `prune: false` on `argocd-self-managed` means a stale CM is left alone rather than
  deleted; break-glass is `argocd --core` against the cluster kubeconfig, already
  documented in `platform-gitops/argocd/values.yaml` lines 28-32.
- *A hand-written fragment widens access.* Mitigation:
  `validate-argocd-tenant-rbac.py` pins fragments to the canonical form, which is
  strictly stronger than today's prose comment.
- *An operator edits `values.yaml` out of habit and reintroduces a tenant block.*
  Mitigation: the same gate fails on any `role:team-` line in `values.yaml`.
- *A tenant created after the migration is silently un-migrated on rollback.*
  Mitigation: the rollback note in `tasks.md` requires re-adding such a tenant's six
  lines to `values.yaml` in the revert commit.
- *Docs drift.* `docs/soc2/access-review.md` step 4 points auditors at
  `platform-gitops/argocd/values.yaml` for tenant `exec`; it must be updated to
  point at `platform-gitops/argocd/rbac/tenants/` and at the new gate.

## Top-3 (for spec-writer)

### 1. argocd-annotation-xss-privesc: Patch Argo CD stored XSS in link annotations (CVE-2026-45738)
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** New CVE this cycle, distinct vulnerability class from the already-tracked ServerSideDiff/secret-disclosure CVEs (`argocd-serversidediff-secret-exposure/-leak`, `argocd-secret-leakage-patch`): here an app-write user injects JS via `link.argocd.argoproj.io/*` annotations that executes in an admin session, i.e. a developer-to-admin privilege-escalation path. Fix versions (3.2.12/3.3.10/3.4.2) overlap with the recap CVEs, so this can piggyback on the same version-pin bump already planned, but the RBAC/privilege-escalation angle is new and warrants its own spec so acceptance criteria explicitly cover annotation sanitization, not just secret exposure.
**Source:** https://osv.dev/vulnerability/BIT-argo-cd-2026-45738

### 2. cert-manager-acme-rbac-bypass: Restrict ClusterIssuer DNS-credential exposure via ACME Challenge/Order RBAC (CVE-2026-62290)
**Category:** security
**Impact:** 4
**Effort:** 3
**Rationale:** New CVE this cycle and a different bug class from the already-covered `cert-manager-dns-dos-patch` (DNS-response DoS): the default `edit` ClusterRole lets namespace users create ACME Challenge/Order resources directly, bypassing per-Issuer DNS01-solver policy and reaching ClusterIssuer DNS credentials — CVSS 7.3. Our fleet's latest scanned release (1.21.2) postdates the fix range (1.19.6/1.20.3), but the spec needs to confirm the actually-pinned version and, per the CVE's own recommendation, review whether the default `edit` ClusterRole binding needs tightening in our tenant RBAC, which is control-plane work and does not touch tenant workload memory.
**Source:** https://osv.dev/vulnerability/BIT-cert-manager-2026-62290

### 3. argo-workflows-cred-log-leak: Confirm and remediate Argo Workflows artifact-credential plaintext logging (CVE-2026-42295)
**Category:** security
**Impact:** 4
**Effort:** 2
**Rationale:** Not surfaced in any prior cycle — genuinely new finding, distinct from the recapped strict-mode/info-disclosure CVEs already tracked under the generic `argo-workflows-cve-bundle-upgrade`/`argo-workflows-cve-patch(-v2)` proposals. The executor logging S3/GCS/Azure/Git credentials in plaintext during artifact operations (affecting 4.0.0-<4.0.5) is a real secret-exposure risk if any log-access is broader than intended; our fleet on 4.1.2/4.1.3 likely postdates the fix, so the spec is mainly a confirmation/audit task (verify pinned version, check for already-leaked creds in historical logs, rotate if needed) rather than a full patch — kept low effort.
**Source:** https://cve.imfht.com/detail/CVE-2026-42295?lang=en

**Tenant-labs note:** all three picks are control-plane/security fixes (ArgoCD, cert-manager, Argo Workflows controller/executor) with no expected increase in tenant workload memory footprint; none flagged as risky for the `labs` memory-limit constraint.

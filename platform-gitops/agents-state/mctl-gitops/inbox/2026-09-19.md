## Top-3 (for spec-writer)

### 1. argo-workflows-strict-mode-bypass-ghsa-3775: Argo Workflows templateReferencing Strict/Secure-mode bypass (GHSA-3775-99mw-8rp4)
**Category:** security
**Impact:** 5
**Effort:** 3
**Rationale:** This is an incomplete fix for a previously patched CVE (CVE-2026-31892): `templateReferencing` Strict/Secure mode — the primary guardrail against untrusted-template privilege escalation in Argo Workflows, which we run for all cron/on-demand pipelines per `architecture.md` — can still be bypassed via `hostNetwork`, `securityContext`, or `serviceAccountName` fields. No fix version is published yet, so the proposal should cover an interim admission-policy mitigation (block those fields on WorkflowTemplates from untrusted sources) plus tracking the upstream patch, rather than a simple version bump. Genuinely new this cycle and directly hits a component we run in production.
**Source:** https://github.com/argoproj/argo-workflows/security/advisories/GHSA-3775-99mw-8rp4

### 2. eso-cve-2026-42876-sa-impersonation-patch: Upgrade External Secrets Operator to remediate service-account impersonation (CVE-2026-42876)
**Category:** security
**Impact:** 4
**Effort:** 2
**Rationale:** CVE-2026-42876 lets a user with only `ExternalSecret` create/update permissions make the ESO controller mint a Secret populated with a long-lived token for an arbitrary service account, enabling SA impersonation without direct RBAC on that SA (fixed 2.4.1, already covered by tracked upstream latest v2.11.0). ESO manages all tenant/platform secrets via `vault-backend` per `architecture.md`, so this is high impact for low effort (version bump). **Narrowed from the original pairing with CVE-2026-34984 (DNS exfiltration)** — orchestrator cross-checked `proposals/` (analyst's Glob against that directory returned empty in its sandbox, so it could not do this itself) and found `proposals/eso-dns-exfil-patch/requirements.md` already covers CVE-2026-34984 verbatim (same CVE ID, same v2 template-engine `getHostByName` mechanism, same fix version 2.2.1) and is still unimplemented (no `.status.yaml`). Re-proposing it would be pure duplication, so only the genuinely uncovered CVE-2026-42876 remains in scope here.
**Source:** https://cve.report/CVE-2026-42876

### 3. loki-v3-7-8-dependency-cve-bump: Bump Loki to v3.7.8 (security-only dependency patch)
**Category:** security
**Impact:** 3
**Effort:** 1
**Rationale:** Loki v3.7.8 is a security-only release bumping `google.golang.org/grpc` to v1.83.2, `containerd/v2` to v2.2.8, and `golang.org/x/net`/`x/crypto` — 7 dependency-vulnerability fixes with no functional changes, low effort to adopt. Orchestrator substituted this in place of the analyst's original pick 3 (`vault-2.1.1-security-upgrade`): that item targeted the same three CVEs (CVE-2026-3605, CVE-2026-5052, CVE-2026-5807) already covered by the existing, unimplemented `proposals/vault-v2-major-upgrade-plan/` (verified by reading its requirements.md), making it a near-duplicate rather than new work; Loki's dependency bump is unrelated to any existing Loki proposal (`loki-ruler-path-traversal` addresses a different, already-fixed CVE — CVE-2026-21726 path traversal) and was previously only dropped for being lower-priority than Vault, not for being covered.
**Source:** https://github.com/grafana/loki/releases/latest

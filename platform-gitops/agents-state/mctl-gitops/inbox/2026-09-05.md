## Top-3 (for spec-writer)

### 1. argocd-serversidediff-secret-exposure: Patch/confirm Argo CD version against ServerSideDiff cleartext-Secret CVEs
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** CVE-2026-43824 and CVE-2026-42880 (both CVSS 9.6) let a read-only ArgoCD user or the ServerSideDiff code path read cleartext Kubernetes Secret data — this directly undermines the "no hardcoded secrets, all via Vault + ExternalSecrets" convention in `context/architecture.md`, since it's exactly the Secret objects ESO renders that would be exposed. Our own context/current-version.md does not pin an exact deployed Argo CD version, so per the "confirm/patch to safe version" guidance the actionable spec is: verify the deployed Argo CD build against the affected ranges (3.2.0-3.2.11, 3.3.0-3.3.9) and pin to a patched minor (the researcher's own newest-release scan already shows 3.5.2, which postdates the fix) rather than doing an unrelated major upgrade. This is a version-pin/manifest change in `platform-gitops/apps/`, not a pattern change, so it doesn't conflict with ADR-0001.
**Source:** cve — CVE-2026-43824 (https://juliet.sh/blog/we-tested-argocd-cve-2026-43824-serversidediff-secret-exposure), CVE-2026-42880 (https://securityonline.info/argo-cd-critical-secret-leak-cve-2026-42880-kubernetes-security/)

### 2. eso-getsecretkey-cross-namespace-secret-leak: Bump External Secrets Operator chart past CVE-2026-22822
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** External Secrets Operator is the platform's sole sanctioned mechanism for delivering secrets from Vault (per architecture conventions), so a critical (CVSS 8.8) flaw in it is a direct hit on the platform's secret-isolation model: the `getSecretKey` template function abused the controller's elevated RBAC to exfiltrate secrets across tenant namespaces (relevant across `admins`/`labs`/other tenant boundaries), fixed by removing that function in 1.2.0. A newer chart (`helm-chart-2.10.0`, released Aug 28, 2026) is already out, so this is a straightforward chart-version bump in `platform-gitops/argo-workflows/secrets/` / wherever the ESO chart is pinned, not an architecture change. Memory footprint of the ESO controller itself is negligible and this patch does not increase `labs` memory usage — not a risk to the near-limit `labs` quota.
**Source:** cve — CVE-2026-22822 (https://vulert.com/vuln-db/CVE-2026-22822); github releases — external-secrets helm-chart-2.10.0 (https://github.com/external-secrets/external-secrets/releases/latest)

### 3. argocd-repo-server-rce-network-isolation: Add NetworkPolicy to restrict access to Argo CD repo-server's internal port
**Category:** security
**Impact:** 5
**Effort:** 3
**Rationale:** An unauthenticated attacker with network reach to the repo-server's internal port can achieve remote code execution; this was reported to maintainers in Jan 2025 and remains unpatched as of the July 2026 disclosure, so there is no version bump available as a fix. The actionable mitigation that belongs in this GitOps repo is a Kubernetes NetworkPolicy manifest limiting ingress to the repo-server pod to only `argocd-server`/`argocd-application-controller`, which can be authored and applied via the existing raw-YAML/App-of-Apps flow without touching the ApplicationSet pattern itself (respecting ADR-0001's "what not to propose" list — no gates, no Flux migration, no pattern change). The repo-server runs in the ArgoCD control-plane namespace, not in `labs`, so this change does not affect the `labs` memory budget.
**Source:** cve — Argo CD repo-server unauthenticated RCE, no CVE assigned (https://thehackernews.com/2026/07/unpatched-argo-cd-repo-server-flaw.html)

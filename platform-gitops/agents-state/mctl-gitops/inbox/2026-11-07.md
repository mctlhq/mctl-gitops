### 1. argocd-repo-server-hardening: Lock down Argo CD repo-server (NetworkPolicy and Kustomize-Helm config)
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** Two critical Argo CD repo-server issues (CVE-2026-15416, unauthenticated gRPC code execution, and CVE-2026-113709, CVSS 9.9, repo-controlled Kustomize Helm config home) have config-only mitigations. Argo CD is the sync engine for the whole platform and this repo is its source, so a repo-server compromise has the widest blast radius. The work is a NetworkPolicy restricting repo-server gRPC and Redis to Argo CD components, plus disabling `--enable-helm` for kustomize builds (or pinning helmGlobals.configHome outside the repo) after checking that no current App relies on it. It needs no version bump, so it does not conflict with the "no Argo major upgrade on patch-day" rule. It adds no pods, so there is no labs memory impact. **Needs verification:** CVE-2026-15416 and CVE-2026-113709 IDs, and whether the running Argo CD version is in the affected range (the running version is not in `context/`; check via mctl or the cluster).
**Source:** cve section: CVE-2026-113709 (strix.ai), CVE-2026-15416 (Red Hat).

### 2. argocd-patch-serversidediff-fix: Move Argo CD to a patched release within its current minor line
**Category:** security
**Impact:** 4
**Effort:** 3
**Rationale:** The ServerSideDiff secret-disclosure family (CVE-2026-45737, CVE-2026-42880, CVE-2026-43824) leaks Secret values and is fixed in 3.2.12, 3.3.10 and 3.4.2 (and 3.3.9 / 3.2.11 for 42880). The proposal should be a same-minor patch bump, staged on admins first, and must not be a major or minor jump (see architecture "What NOT to do" and the Argo 3.7.10 archive bug history). Its first step is to check whether ServerSideDiff is enabled at all; if it is not, urgency drops and the item can be downgraded. The latest release (v3.6.1) is only a UI/rootpath fix and is not itself a reason to upgrade. Argo CD runs in admins, not labs, but a rolling restart should be checked against labs quota before rollout. **Needs verification:** all three CVE IDs and the fixed-version list.
**Source:** cve section: CVE-2026-45737 (SentinelOne), CVE-2026-42880 / CVE-2026-43824 (securityonline.info); release argo-cd v3.6.1.

### 3. emudhra-ca-distrust-bumps: Roll out cert-manager v1.21.3, Vault v2.2.1 and Argo Rollouts v1.10.2 for the eMudhra CA distrust
**Category:** security
**Impact:** 3
**Effort:** 3
**Rationale:** Three core components shipped coordinated fixes for the compromised eMudhra CA, and cert-manager v1.21.3 also fixes an ACME ARI renewal loop and a Secret private-key copy issue. Vault v2.2.1 also rejects policy aliases that resolve to the root policy. Impact is capped at 3 because the platform likely does not chain to eMudhra, so this is mostly trust-store hygiene. The spec should check exposure first, then stage: cert-manager, then Argo Rollouts, then Vault last with a snapshot and its own rollback, since Vault holds all platform secrets via the `vault-backend` ClusterSecretStore. **Risk flag:** the Go 1.26.10 toolchain bump in cert-manager and Argo Rollouts may shift controller memory slightly, so the spec must measure memory in `labs` (close to its limit) before and after rollout and use a canary. Do not bundle the unrelated Vault SPIFFE feature. **Needs verification:** CVE-2026-111943 (six-digit ID, unverified) and that the current Vault/cert-manager/Rollouts versions are behind these releases.
**Source:** releases section: cert-manager v1.21.3, vault v2.2.1, argo-rollouts v1.10.2; cve section: eMudhra CA distrust.

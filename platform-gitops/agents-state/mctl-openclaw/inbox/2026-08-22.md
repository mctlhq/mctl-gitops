## Top-3 (for spec-writer)

### 1. labs-s3-sync-silent-canary: Investigate zero s3-sync log output for `labs`/openclaw
**Category:** security
**Impact:** 4
**Effort:** 2
**Rationale:** `mctl_get_service_logs` returned 0 lines for the `labs` openclaw s3-sync container across both a 1h and a 6h window, while `admins` and `ovk` show normal sync activity in the same sampling method — this is exactly the class of signal CLAUDE.md flags to watch closely (s3-sync canary health). Per ADR-0002, an undetected s3-sync failure is the precise footgun that causes silent auth/session loss on the next `labs` restart, and `labs` is the designated canary tenant ahead of `ovk` (ADR-0001), so a broken canary there defeats its purpose. This is an investigation task (log/pod/container-name verification, canary CronWorkflow status check), not a code change — it adds no memory footprint to `labs` and does not propose replacing S3, disabling the canary, or shortening the probe timeout (respects ADR-0002 constraints).
**Source:** inbox "Source: mctl metrics" — s3-sync canary section (labs vs admins/ovk).

### 2. plugin-sdk-migration-discord-compat: Plan Plugin SDK migration ahead of before_agent_start deprecation and validate Discord plugin registration
**Category:** refactor
**Impact:** 4
**Effort:** 3
**Rationale:** openclaw 2026.7.2-beta.7 deprecates `before_agent_start` hooks and legacy plugin imports that the fork's `extensions/*` still use via `openclaw/plugin-sdk/*`; deployed tenants are already on 2026.7.11-beta.2, close to this breaking line, and the currently-tracked context/current-version.md (2026.3.14) is stale, so the fork's real exposure window is narrower than the static docs suggest. Compounding this, upstream issue #122655 shows the official Discord plugin itself fails to register on core 2026.8 after the same SDK export changes — directly relevant because Discord is a channel we run in all three tenants. Migration work should be scoped, validated in `labs` first per ADR-0001's rollout order, and should not increase `labs` memory footprint as part of the migration.
**Source:** inbox "Source: github releases" (openclaw 2026.7.2-beta.7) and "Source: github issues" (#122655).

### 3. baileys-cve-48063-version-check: Confirm fork's vendored Baileys version against CVE-2026-48063 and upgrade if exposed
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** CVE-2026-48063 (CVSS 9.3, critical) allows message/history spoofing and app-state corruption on WhatsApp Web sessions via a crafted `placeholderResendMessage` payload, fixed only in Baileys ≥6.7.22 / ≥7.0.0-rc12; WhatsApp is a channel the fork actively runs across all tenants, so this is high-severity and architecturally relevant. Upstream Baileys "latest" tag is already 7.0.0-rc14 (post-fix), but the researcher could not confirm which version the fork vendors, so a quick version check (and dependency bump if needed) is low effort relative to the severity, and a version bump alone should not measurably raise `labs` memory usage.
**Source:** inbox "Source: cve" — CVE-2026-48063.

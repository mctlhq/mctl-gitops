## Top-3 (for spec-writer)

### 1. ghsa-batch-2026-09-11-upgrade-assessment: Assess and patch the September 11 GHSA batch (WhatsApp/Discord/Slack/exec-approval advisories)
**Category:** security
**Impact:** 5
**Effort:** 4
**Rationale:** On 2026-09-11 upstream published 10 official GHSA advisories, including High-severity findings directly hitting channels we run in production (WhatsApp login tool reaching non-owner turns, exec approvals outliving their reviewed working directory) plus Moderate advisories on Discord asset uploads and Slack file downloads — all architecturally in scope per `context/architecture.md`. Our deployed baseline (`2026.7.11-beta.2` per `mctl_get_service_status`, two release trains behind current upstream) predates these fixes, and issue #151054 confirms the LTS 2026.6.35 release notes don't even disclose which of the 10 are backported there, so we cannot assume safety without an explicit version check. Note: `context/current-version.md` still says `2026.3.14` and is visibly stale (last updated 2026-04-26) — the spec-writer should treat the mctl-reported `2026.7.11-beta.2` as ground truth and update that file as part of the work. This does not conflict with ADR-0001 (rollout must still go `labs` → `admins` → `ovk`) or ADR-0002 (canary/probe stay in place during rollout).
**Source:** "10 official GHSA security advisories published 2026-09-11" (cve section); "Deployed baseline unchanged since Aug 22 ... 2026.7.11-beta.2" and issue #151054 (github releases / github issues sections), inbox 2026-09-19.md.

### 2. ovk-s3-sync-canary-and-pod-health-investigation: Investigate silent s3-sync canary and possible pod-down state in `ovk`
**Category:** security
**Impact:** 5
**Effort:** 2
**Rationale:** `ovk` is the production, high-SLA tenant where ADR-0002 explicitly says auth/session loss cannot be tolerated, and this pass shows three simultaneous anomalies for `ovk`/openclaw that didn't co-occur on Aug 22: zero s3-sync log lines (previously only `labs` showed this), a sharp resource-usage drop (limits.memory ~81%→~17%, pods used 2/5→1/5), and ArgoCD reporting `OutOfSync`/Healthy — with zero incidents raised. Individually any one of these could be noise, but together they suggest the openclaw pod in `ovk` may be down or degraded without alerting, which is exactly the blind spot the s3-sync canary and restore-state probe exist to catch per ADR-0002. This is a read-only diagnostic task (check pod status, canary CronWorkflow history, ArgoCD diff) with no code change and no memory impact on any tenant, so it carries low effort and no risk to `labs`.
**Source:** "ArgoCD sync status", "s3-sync canary — `labs` and `ovk` both returned 0 log lines", "ovk resource usage — ... Large drop vs Aug 22" (mctl metrics section); "ovk: 0 active incidents ... no incident has fired despite the metrics shift" (mctl incidents section), inbox 2026-09-19.md.

### 3. labs-memory-quota-trend-review: Review and alert on `labs` tenant-wide memory quota trend before it blocks rollouts
**Category:** performance
**Impact:** 3
**Effort:** 2
**Rationale:** `labs` tenant-wide memory usage jumped from ~60% to ~83% of its `limits.memory` quota (and requests.memory from ~62% to ~76%) between Aug 22 and this pass, with CPU limits now at ~94% — a meaningful escalation for a tenant the platform already treats as close to its limit. Per ADR-0001, `labs` is the mandatory canary tenant every change must pass through before `admins`/`ovk`, so if it runs out of headroom it becomes a rollout bottleneck for everything else, including finding #1 above. This is a monitoring/investigation task (identify which of the 17 services is driving the growth, add an early-warning alert threshold) rather than a change that itself adds footprint, so it does not violate the "no increase in `labs` memory" constraint — quite the opposite, it's meant to protect it.
**Source:** "labs resource usage — up notably vs Aug 22 ... ~83% ... was ~60%" (mctl metrics section), inbox 2026-09-19.md.

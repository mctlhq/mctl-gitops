# Design: issue-1094-ci-release-publish-the-agent-worker-imag

## Current state
- `.github/workflows/preview-deploy.yml` (on push to `main`) mints an `mctl-agents` App token scoped to `mctl-gitops` and runs two `gh workflow run release-deploy.yaml` steps:
  1. "Dispatch preview release-deploy": `image_name=ghcr.io/mctlhq/mctl-telegram`, `image_tag=main-${SHA::7}`, `component_name=mctl-telegram-preview`.
  2. "Dispatch agent-worker preview release-deploy": `image_name=ghcr.io/mctlhq/agent-worker-preview`, same tag, `dockerfile_path=Dockerfile.agent-worker`, `component_name=agent-worker-preview`. Its comment explains why the tag matches the server's and that parallel runs rebase-retry their gitops push.
- `.github/workflows/release-please.yml` job `release-please`: after `googleapis/release-please-action` and, gated on `steps.release.outputs.release_created == 'true'`, it runs "Generate Platform App token" (`id: app`) and then "Dispatch centralized release-deploy" (server image only: `image_name=ghcr.io/mctlhq/mctl-telegram`, `image_tag=$TAG`, `component_name=mctl-telegram`). The Local Bridge cross-compile and `gh release upload` follow. Their comment says they run last on purpose so that they do not delay deploy dispatches. Tags have no `v` prefix (`release-please-config.json`: `include-v-in-tag: false`).
- `.github/workflows/build.yml` job `docker-agent-worker` builds `Dockerfile.agent-worker` with `push: false` and cache scope `agent-worker` as a PR check. This job is left as is.
- `docs/adr/0008-managed-runtime.md` section 6: preview component `agent-worker-managed-preview` in `labs` uses the same image as `agent-worker-preview`. Production uses `ghcr.io/mctlhq/agent-worker:<tag>` published by the release workflow.
- Precedent for testing workflow YAML from Go: `cmd/login-proof/workflow_test.go` reads `../../.github/workflows/*` with `os.ReadFile`, checks invariants by string inspection, and has a mutation test (`TestProofWorkflowGuardCatchesMutations`) that proves the guard fails when each invariant is broken. That matches the issue's rule that every regression test must fail with the bug reintroduced.
- mctl-gitops `.github/workflows/release-deploy.yaml` (read at `/workdir/mctl-gitops/.github/workflows/release-deploy.yaml`): it validates inputs (including `dockerfile_path`), calls `build-image.yaml` (build and push, with no skip-if-tag-exists), and then updates `platform-gitops/services/<team>/<component>/values.yaml` unless `values_path` is given. That value may be a comma-separated list. A missing file exits 2 (`ERROR: file(s) not found`). The workflow has no `concurrency` group.

Deployed state checked:
- `$MCTL_GITOPS_ROOT/services/labs/` lists `agent-worker-preview`, `mctl-telegram` and `mctl-telegram-preview`. Neither `agent-worker-managed-preview` nor `agent-worker-managed` exists yet. The sibling proposal `agents-state/mctl-telegram/proposals/issue-1090-.../design.md` records the same gap.
- `$MCTL_GITOPS_ROOT/services/labs/agent-worker-preview/values.yaml`: `image.repository: ghcr.io/mctlhq/agent-worker-preview`, `tag: "main-84f7c55"` (auto-bumped by preview-deploy.yml), `replicaCount: 0` since 2026-10-29 (the worker runs off-cluster). This confirms the preview image name and tag format the new dispatch must reuse.
- I did not call the mctl MCP tools. The gitops checkout was enough for this CI-only change, and no runtime state is asserted here.

## Proposed solution
0. Gitops existence guard (owner amendment 2026-11-03). New script `.github/scripts/gitops-values-present.sh <values-path>`:
   - Reads `${GITHUB_API_URL:-https://api.github.com}/repos/mctlhq/mctl-gitops/contents/<values-path>?ref=main` with `curl -sS -o /dev/null -w '%{http_code}'`, authenticated with `Authorization: Bearer $GH_TOKEN` (the step's existing App token; installation permissions already include contents read on mctl-gitops, no `permission-*` change).
   - Exit codes: `0` = HTTP 200 (present); `3` = HTTP 404 (absent, the documented absence signal); `1` = anything else, which covers any other status, a curl transport failure (non-zero curl exit), an empty or non-numeric status, and an unset `GH_TOKEN`. It validates `<values-path>` (must start with `platform-gitops/services/`, no `..`, no spaces) and exits 1 otherwise.
   - Each new dispatch step uses it as:
     ```bash
     rc=0; .github/scripts/gitops-values-present.sh "$VALUES" || rc=$?
     case "$rc" in
       0) gh workflow run release-deploy.yaml ... ;;
       3) echo "::notice::$VALUES not on mctl-gitops main; skipping <component> dispatch" ;;
       *) echo "::error::could not read $VALUES on mctl-gitops main (rc=$rc)"; exit 1 ;;
     esac
     ```
     with `VALUES=platform-gitops/services/labs/<component>/values.yaml` for exactly the component it dispatches.
   - The two existing dispatches are not guarded and stay byte-identical.
1. `preview-deploy.yml`: add a third step "Dispatch agent-worker-managed-preview release-deploy" after the agent-worker step, guarded as in item 0 (the job already runs `actions/checkout`, so the script is on disk). The `gh workflow run` inputs are identical to step 2 except `-f component_name=agent-worker-managed-preview`. Add a comment that references ADR 0008 section 6, explains why the image is the same one and why the step is guarded (the component appears with mctl-gitops#2345), and notes that this run builds and pushes the same tag again in parallel. That is harmless because both components pin by tag, are built from the same commit and Dockerfile, and gitops push conflicts are rebase-retried.
2. `release-please.yml`: add "Dispatch agent-worker release-deploy" directly after "Check out the released tag" and before the first Local Bridge `go build` step, so the script is on disk and the existing "run last on purpose" comment stays true. It uses the same `if: release_created == 'true'` gate, `GH_TOKEN: ${{ steps.app.outputs.token }}`, `TAG: ${{ steps.release.outputs.tag_name }}`, is guarded as in item 0 for `platform-gitops/services/labs/agent-worker-managed/values.yaml`, and dispatches with `repo=mctlhq/mctl-telegram`, `git_ref="$TAG"`, `image_name=ghcr.io/mctlhq/agent-worker`, `image_tag="$TAG"`, `dockerfile_path=Dockerfile.agent-worker`, `team_name=labs`, `component_name=agent-worker-managed`. The comment states that production `agent-worker-managed` does not exist until the production rollout after #889/#334, so until then every release emits the skip notice and no `ghcr.io/mctlhq/agent-worker` image is published. No new permission is needed: the App token already covers the dispatch and the contents read, and the GHCR push happens inside mctl-gitops `build-image.yaml` with `packages: write`.
3. `build.yml`: no change. `docker-agent-worker` stays the no-push PR check.
4. Regression test `cmd/agent-worker/deploy_workflows_test.go` (package `main`, modelled on `cmd/login-proof/workflow_test.go`):
   - It splits a workflow file into `gh workflow run release-deploy.yaml` blocks and parses each `-f key=value` into a map, stripping quotes.
   - `checkDeployWorkflows(preview, release string) []string` requires the following:
     - preview: a block where `component_name=agent-worker-managed-preview`, `image_name=ghcr.io/mctlhq/agent-worker-preview`, `dockerfile_path=Dockerfile.agent-worker`, `team_name=labs` and `image_tag=main-${SHORT_SHA}`. The existing `agent-worker-preview` and `mctl-telegram-preview` blocks must still be present.
     - release: a block where `component_name=agent-worker-managed`, `image_name=ghcr.io/mctlhq/agent-worker`, `image_tag=$TAG`, `git_ref=$TAG`, `dockerfile_path=Dockerfile.agent-worker` and `team_name=labs`. Its step carries the `release_created == 'true'` guard, and it appears after "Check out the released tag" and before `go build` (the Local Bridge step).
     - both new steps: the step that contains the dispatch block calls `.github/scripts/gitops-values-present.sh` with `platform-gitops/services/labs/<component_name>/values.yaml` for the same `component_name`, the `gh workflow run` sits under the `0)` arm, and a `*)` arm ends in `exit 1`. The two existing dispatch steps contain no guard call.
     - build.yml: `docker-agent-worker` still has `file: Dockerfile.agent-worker` and `push: false`.
   - `TestDeployWorkflows` asserts that no violations are found. `TestDeployWorkflowsGuardCatchesMutations` applies each mutation and asserts that the guard fails: delete the managed-preview block, change its component name, change the release image to `agent-worker-preview`, drop `dockerfile_path` from the release block, drop the `if:` guard, move the step after `go build`, set `push: true` in build.yml, remove the existence-guard call from either new step, point the guard at the other component's path, and replace the `*) ... exit 1` arm with a skip. It also asserts that each mutation actually changed the text, as the login-proof test does.
5. Script test `TestGitopsValuesPresent` in the same file runs the real `.github/scripts/gitops-values-present.sh` with `bash` against an `httptest.Server` (via `GITHUB_API_URL`) and asserts: 200 -> exit 0; 404 -> exit 3; 403, 500 and 502 -> exit 1; a closed server (transport error) -> exit 1; unset `GH_TOKEN` -> exit 1 with no request sent; a `..` path -> exit 1 with no request sent; and that the request carries the bearer token and `ref=main`. Mutations stated in the PR, each making this test fail: map every non-200 status to 3 (absent); map every non-404 status to 0; drop the curl exit-code check.

## Alternatives
- One preview build bumping both components via `values_path=platform-gitops/services/labs/agent-worker-preview/values.yaml,platform-gitops/services/labs/agent-worker-managed-preview/values.yaml` on the existing step 2. This avoids a duplicate build and a second push of the same tag. It was dropped as the primary option because the issue and ADR ask for a separate dispatch, and because coupling the two means a missing managed-preview file would fail the `agent-worker-preview` bump too (release-deploy rejects the whole list). It is a reasonable follow-up once both components exist.
- A separate `release: published` workflow that builds the worker image. Dropped: the existing comment in `release-please.yml` explicitly keeps release artefacts on the run that cut the tag. A `release` event from the App token would also be a second, unwatched workflow.
- Pushing `ghcr.io/mctlhq/agent-worker` from `build.yml` `docker-agent-worker` on tags. Dropped: the issue keeps that job as a no-push PR check. All image pushes in this repo go through mctl-gitops `build-image.yaml`, which owns registry credentials and signing.

## Platform impact
- Migrations: none. Backward compatibility: existing dispatches are unchanged.
- Resources: one more Docker build per merge to main (the duplicate agent-worker-preview build) and one more per release, on mctl-gitops runners. A new GHCR package `ghcr.io/mctlhq/agent-worker` is created on the first release push. Its visibility and package permissions follow whatever `build-image.yaml` and the org default produce. Check this after the first release.
- Dispatch before the gitops components exist: handled by the existence guard (item 0). Until mctl-gitops#2345 lands, merges to `main` emit a skip notice for `agent-worker-managed-preview`. Until the production rollout, releases emit one for `agent-worker-managed` and publish no `ghcr.io/mctlhq/agent-worker` image. Both turn on by themselves once the values file is on gitops `main`, with no change in this repo.
- Risk: the check and the dispatched run read gitops `main` at slightly different times. A component deleted in between still fails red in release-deploy, which is the correct signal. A component added in between is picked up on the next merge or release.
- Risk: a GitHub API outage now fails the preview-deploy / release-please job at the guard rather than later in mctl-gitops. This is intended: an unobserved component is never treated as absent. The existing server dispatches run earlier in the same job and are unaffected.
- Risk: two parallel builds push `agent-worker-preview:main-<sha>`, so the tag may end up pointing at the digest of the later build. Both are built from the same commit and Dockerfile. Pods pin by tag and `agent-worker-preview` is at `replicaCount: 0`, so impact is negligible.
- Note: production `agent-worker-managed` would start from the first release once its gitops values exist. The ADR gates production on #889 and #334. Mitigation: the gitops side should land with `replicaCount: 0`, which is outside this repo.

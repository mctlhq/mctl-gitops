## Tests

The split follows the rule in design.md "Verification tiers": correctness,
privacy and security, unchanged run semantics and backward compatibility are
required before merge; multi-process fault matrices and operational
confirmation are required before the pilot GO.

### Required before merge

- [ ] T1. Propagation: using `tracetest.SpanRecorder` and the synthetic personas `Alice` and `Bob`, run end-to-end cases through the existing harnesses (`worker_e2e_test.go`, `worker_tools_e2e_test.go`, `worker_approval_e2e_test.go`): success with a tool, no-tool, denied tool (pin refusal), tool approval_pending, turn timeout, and a retry (release, then reclaim as attempt 2). Each case yields one trace per job, with the expected span names, parentage, attempt numbers and outcomes.
- [ ] T2. Untrusted metadata: a webhook request and run-loop requests carrying a forged `traceparent`, `tracestate` or `baggage` produce spans only under the stored server context. The forged trace id never appears.
- [ ] T3. Cross-principal isolation: concurrent jobs for `Alice` and `Bob` (worker `WithConcurrency(2)`) never share a trace id, and no span of one job is parented to the other's.
- [ ] T4. Redaction and no downstream leakage: walk every recorded span and its events. Every attribute key must be in the `runAttrs` allowlist. No attribute value may contain the fixture principal ids, message text, tool arguments, tool output or token strings. Also assert that downstream MCP requests (`connector/mcpclient_test.go`), the worker's provider requests and Bot API requests carry no `traceparent`, `tracestate`, `baggage`, trace id or job id.
- [ ] T5. Bounded cardinality: gather the metrics registry after the T1 cases and assert that the label values of the new and extended families are subsets of the closed sets, with no id-like label.
- [ ] T6. Absent and partial stage: a no-tool run observes no `tool` phase and no `tool_call` stage. A run whose reply has not been delivered yet observes no `delivery` phase. A run with an unknown `created_at` observes no `queue` or `total` phase and counts `partial`/`unknown_created_at`. A terminal transition with no local timer entry counts `partial`/`timer_missing`, and a pre-migration row counts `missing`/`no_trace_context`. Nothing is observed as 0.
- [ ] T7. Unchanged semantics: the existing `internal/pa`, `internal/pa/connector`, `internal/pa/jobs`, `internal/db` and `internal/agentworker` suites pass with tracing on and with it off. One table-driven test asserts that the HTTP status codes, release modes and failure reasons are identical in both modes for the lease-short, lease-expired, fenced (`StillRunning`) and cancel cases.
- [ ] T8. Collector failure and kill switch: an exporter pointed at a blackholed endpoint does not add latency above a small bound to `serveClaim`, `serveReply` or `deliverItem`, does not fail them, and counts drops. A forced tracing error (setup failure, unparsable stored context) leaves authorization, job results and delivery unchanged. With `PA_TRACING_ENABLED=false` no exporter starts and no connection is opened.
- [ ] T9. Migration and compatibility: `pa_jobs` migrates on SQLite and Postgres (the existing `internal/db` migration tests), and old rows read `''`. An old worker against a new server and a new worker against an old server both complete runs unchanged.
- [ ] T10. Duplicate observation (single process): two terminal transitions for the same job (for example reply racing cancel) record one terminal observation and one `pa.job` span; the losing request records only its refused span.

### Required before pilot GO

- [ ] P1. Restart: a server restart between enqueue and claim, and another after claim, still yields one trace per job; the affected observations are `partial`, never 0.
- [ ] P2. Split replica: claim on one server process and reply on another (two in-process servers on one database) yields one `pa.job` span from the terminal winner and a `partial` attempt span, with no duplicate terminal observation.
- [ ] P3. Retry, fencing and lease expiry matrix across processes: release then reclaim, a fenced stale reply, and lease expiry followed by reclaim each produce sibling attempt spans, one terminal observation and unchanged status codes and release modes.
- [ ] P4. Privacy, retention and deletion: task 11 values are recorded and accepted; account deletion removes `pa_jobs.trace_context`; the runbook states how long exported spans and logs outlive it. This is also the hard precondition for task 10.
- [ ] P5. Dashboards: task 12 is done with mctlhq/mctl-telegram#1446 and mctlhq/mctl-gitops#3004.

## Rollback

- Tracing: set `PA_TRACING_ENABLED` to `"false"`, or `otel.enabled: false` in gitops. The provider becomes a no-op at the next restart. No code rollback is needed.
- Code: revert the PR(s). The `trace_context` column is additive and harmless to leave in place, and older binaries ignore it. Drop it in a later migration only if needed.
- Metrics: the new families disappear with the revert. `mctl_pa_run_phase_seconds` keeps its original labels apart from `delivery`, so dashboards built on the old phases keep working throughout.
